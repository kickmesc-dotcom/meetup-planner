# Ручная приёмка AAA: что осталось за владельцем

Дата: **13.11.2026**. Здесь собраны все пункты `docs/AAA_ROADMAP.md`, которые
нельзя закрыть кодом и тестами: нужен живой аккаунт, живой человек или доступ
к панелям. Документ — рабочая форма: идти сверху вниз, отмечать результат и
записывать найденное.

Что уже закрыто автоматикой и перепроверять руками не нужно:
`axe` на 8 экранах, 43 e2e-сценария, пиксельная регрессия в Linux-контейнере,
Lighthouse входа в CI (perf 98, a11y 98, LCP 2,3 с), бюджет бандла, офлайн-старт.

## 0. Подготовка: аккаунт с демо-организацией (5 минут, один раз)

Без этого не проходят пункты 1–4: часть экранов закрыта входом.

1. Открыть `https://semitaskbot.pages.dev/`.
2. Войти любым способом из `docs/ACCOUNTS_AND_ROLES.md`: Telegram Mini App,
   ссылка `?access=…` или почта и пароль.
3. Если организации нет — на стартовом экране «Создать организацию»:
   название (например, «Демо-кофейня»), отрасль.
4. Пригласить второго человека (сотрудника) — иначе сценарии с поручениями
   и приёмкой будут односторонними.
5. Создать одну задачу и один чек-лист, закрыть смену.

**Пройдено, если:** после повторного входа открывается лента с созданной
задачей, а в кабинете видна организация и приглашённый сотрудник.

## 1. Скорость: лента и кабинет

Lighthouse в CI меряет только входной экран: лента и кабинет переключаются
состоянием, а не URL, и закрыты входом (`frontend/lighthouserc.cjs`). Для них
источник правды — RUM: `web-vitals` из живых браузеров уже отправляется на
`POST /api/telemetry/vitals`, а сводка лежит в продукте.

### 1.1. Реальные цифры (главное)

1. Войти, открыть кабинет → раздел «Платформа» → «Скорость у людей».
2. Смотреть p75 за 24 часа по мобильным и десктопу отдельно.

**Пройдено, если:** p75 LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1, TTFB ≤ 0,8 с.
Если данных мало (новый деплой), сначала пройти пункт 4 — телефон наберёт
выборку.

### 1.2. Дополнительно: Lighthouse на ленте

1. Chrome → DevTools → Lighthouse → Mobile, категории Performance +
   Accessibility → Analyze.
2. Повторить на экране ленты после входа.

**Важно:** на залогиненном экране LCP и TBT искажены (шрифты и чанки уже в
кеше, вход не входит в замер). Эти цифры — для поиска грубых проблем, не для
вердикта. Вердикт — по RUM из 1.1.

**Пройдено, если:** a11y ≥ 95 и нет ошибок в консоли. Расхождение LCP с RUM
объяснимо кешем; расхождение a11y — дефект.

## 2. NVDA (Windows), сценарий «вход → задача → смена»

1. Установить NVDA (бесплатно), запустить, Chrome.
2. Включить «Режим обзора» (Browse mode) и пройти: вход → лента → задача →
   чек-лист → закрытие смены.

Проверить по пунктам:

- [ ] Заголовок экрана читается первым и называет место («Лента», «Задачи»).
- [ ] Tab идёт по логическому порядку; фокус видим на каждом шаге.
- [ ] Кнопки произносят действие, а не «кнопка» («Закрыть смену», не «ОК»).
- [ ] Чек-лист объявляет состояние пункта (отмечен / не отмечен).
- [ ] Диалог объявляет заголовок при открытии и возвращает фокус при закрытии.
- [ ] Ошибка формы читается и связана с полем (`aria-describedby`).
- [ ] Сворачивание/раскрытие группы объявляет `expanded/collapsed`.

**Пройдено, если:** ни один шаг не заставляет переключаться в режим форм
вслепую, и ни одна кнопка не звучит безымянно.

## 3. VoiceOver (iOS)

1. Настройки → Универсальный доступ → VoiceOver.
2. Safari → прод → вход → лента → задача → чек-лист.

- [ ] Свайп вправо проходит все элементы, порядок совпадает с визуальным.
- [ ] Ротор находит заголовки и кнопки.
- [ ] Жест «назад» не конфликтует со свайпом по дням.
- [ ] Подсказки полей читаются до ввода, а не после.

**Пройдено, если:** сценарий проходится без помощи зрения.

## 4. Телефон с боевым аккаунтом

Нужен реальный телефон (Android или iPhone) и прод-аккаунт из пункта 0.

1. Открыть прод, войти, пройти ленту и задачу.
2. Включить авиарежим, обновить страницу: должна открыться оболочка с
   понятным сообщением, а не белый экран.
3. Выключить авиарежим, повторить действие.
4. Вызвать ошибку (например, отправить форму в авиарежиме) и засечь время.

**Пройдено, если:** ошибка появилась в логах Amvera в течение минуты, а
RUM-событие — в сводке «Скорость у людей»; офлайн показывает объяснение.

## 6. Инфраструктура (панели, не код)

### 6.1. Branch protection

GitHub → Settings → Branches → правило для `main`:

- [ ] Require a pull request before merging.
- [ ] Require status checks (в списке они по отображаемым именам):
      `Backend (pytest)`, `Frontend (types, tests, build)`,
      `Visual regression (Linux baseline)`.
- [ ] Require branches to be up to date.
- [ ] Do not allow force pushes и deletions.

**Пройдено, если:** прямой push в `main` отклоняется, а красная джоба блокирует
merge.

### 6.2. Старые деплои Pages

Cloudflare → Workers & Pages → `semitaskbot` → Deployments: оставить текущий,
остальные удалить.

**Пройдено, если:** ассет старого деплоя (`/assets/index-<старый хеш>.js`)
отдаёт 404, а прод отвечает 200.

### 6.3. Neon → Amvera Managed PostgreSQL

По `docs/INFRA_CHOICE.md`. Репетиция уже проведена — `docs/CUTOVER_REHEARSAL.md`
(цель и откат проверены на приложении). Остаётся переключить `DATABASE_URL` на
новую базу, догнать `alembic upgrade head`, проверить `/healthz`, `/readyz` и
`/api/meta`, сутки не выключать Neon как точку возврата.

**Пройдено, если:** один боевой хост и одна база, старый Neon выключен после
суток стабильной работы.
