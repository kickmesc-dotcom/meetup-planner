# Бэкапы и восстановление

Шаг 5.4 плана `B2B_PLATFORM_PLAN.md`. Инструменты — `tools/backup-db.py`,
`tools/db-rehearsal.py`; расписание — `.github/workflows/backup.yml`.

## Зачем шаг

Критерий: **восстановление проверено, а не обещано.** «Бэкапы настроены» —
это утверждение о процессе, а не о данных: файл может быть, а данных в нём не
быть. Поэтому здесь важны три вещи: бэкап снимается сам, он снимается с
**боевой** базы, и его **восстанавливали** — в чистую базу, построчно сверив.

## Что нашлось 03.11.2026

- Единственный дамп был снят **29.09.2026** на миграции `0022` — 33 таблицы,
  531 строка. Боевая база ушла на `0067`: за месяц схема выросла на 52
  ревизии, а точки отката не появилось.
- `tools/backup-db.py` брал DSN из `secrets/Get-Secret.ps1`, а тот указывал на
  **старую** базу (`ep-cool-union…`, миграции `0028`). То есть запуск «бэкапа»
  снял бы копию не того сервера — и это худший вид бэкапа: файлы на месте, хэши
  сходятся, откатиться нельзя.
- Сами инструменты жили **вне репозитория**: их не было в git, CI их не видел,
  и на другой машине их бы просто не оказалось.

## Что сделано

1. `tools/backup-db.py` и `tools/db-rehearsal.py` перенесены в репозиторий.
2. `dump` сверяет хост DSN с боевой базой из `/api/meta`. Не совпало — отказ с
   объяснением; копию стенда можно снять только явным `--allow-any`.
   Сравнение идёт по префиксу: боевой DSN идёт через `-pooler`, а `/api/meta`
   маскирует хвост (`ep-dry-cherry-….neon.tech`).
3. `verify` считает пустой дамп ошибкой: целые файлы без строк — не точка
   отката.
4. `prune --keep N` — ротация (по умолчанию 7). Без неё бэкапы занимают диск до
   отказа, а отказ диска — это отказ записи.
5. `db-rehearsal.py rehearse-local` восстанавливает дамп в **одноразовый**
   Postgres в Docker: боевую инфраструктуру не трогаем, мусор не остаётся даже
   при прерванном прогоне.
6. `db-rehearsal.py check DIR --dsn …` — сверка уже восстановленной базы с
   дампом (нужна CI, где Postgres поднимает сам workflow).
7. `.github/workflows/backup.yml`: ежедневный дамп + проверка + артефакт
   (14 дней), раз в неделю — восстановление в чистом Postgres и построчная
   сверка.
8. `backups/` в `.gitignore`: дампы — данные клиентов, им не место в истории.

## Проверено (факт, а не обещание)

**04.11.2026, 00:18 UTC**:

- дамп боевой базы: **85 таблиц, 175 строк, миграции `0067_org_brand`,
  570 kB** — хост сверен с `/api/meta` (`ep-dry-cherry…`);
- `verify`: все sha256 совпали, дамп непустой;
- восстановление: пустой Postgres 16 → `alembic upgrade head` → дамп →
  сверка по каждой таблице: **`✅ ВОССТАНОВЛЕНИЕ ПОДТВЕРЖДЕНО`**,
  **175 строк / 85 таблиц совпали с дампом по каждой таблице**;
- контейнер проверки удалён, боевая база в проверке не участвовала.

## Расписание и RPO/RTO

| Что | Когда | Где |
| --- | --- | --- |
| Дамп + проверка | ежедневно, 03:00 UTC | artifact GitHub, 14 дней |
| Проверка восстановления | воскресенье, 04:30 UTC | чистый Postgres в CI |
| PITR провайдера | история Neon | консоль Neon |

- **RPO (сколько данных можно потерять):** до 24 часов при аварии между
  дампами. Это осознанный компромисс: минутный RPO требует непрерывного
  архивирования WAL, а у нас 11 МБ данных и пилот на несколько человек.
- **RTO (сколько времени восстановление):** минуты. Дамп 570 kB, `restore`
  заливает его в пустую базу за секунды; `alembic upgrade head` — основная
  часть времени.

## PITR

Собственный дамп — **независимая** копия, а не замена PITR: он переживает
удаление базы целиком. PITR даёт провайдер (Neon — история ветки, на бесплатном
тарифе часы, на платном — дни). Проверить фактическое окно нужно **в консоли
Neon**: у нас нет ключа с правами на проект, а обещать «7 дней» без проверки —
ровно та ошибка, от которой этот шаг.

## Как восстановить руками

```bash
# 1. Снять свежий дамп (проверит, что DSN боевой)
DATABASE_URL="<dsn>" backend/.venv/Scripts/python.exe tools/backup-db.py dump

# 2. Проверить целостность
backend/.venv/Scripts/python.exe tools/backup-db.py verify backups/<штамп>

# 3. Проверить восстановление, не трогая боевую инфраструктуру
backend/.venv/Scripts/python.exe tools/db-rehearsal.py rehearse-local backups/<штамп>

# 4. Восстановление в боевую (после аварии; схема должна быть пустой и промигрированной)
DATABASE_URL="<dsn>" backend/.venv/Scripts/python.exe tools/backup-db.py restore backups/<штамп>
```

Порядок восстановления — топологический по внешним ключам, последовательности
выставляются по `max(id)`; без этого первый же обычный `INSERT` падал бы на
дубликате ключа.

## Ограничения, которые нужно знать

- **Секрет `DATABASE_URL` в GitHub Actions добавляет владелец** (Settings →
  Secrets → Actions). До этого ежедневный workflow упадёт на шаге проверки
  секрета — и это правильный сигнал, а не тихий пропуск.
- **Артефакт живёт 14 дней.** Для «ошибки нашли через месяц» нужен внешний
  бакет (R2 уже есть у проекта) — отдельное решение, а не молчаливое обещание.
- **PITR не проверен вживую** (см. выше): нужен доступ к консоли Neon.
- Восстановление проверяется на **нашей** копии, а не наоборот: она не
  доказывает, что провайдер восстановит свою.
