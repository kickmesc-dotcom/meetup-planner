# Лимиты и квоты организации

Шаг 5.3 плана `B2B_PLATFORM_PLAN.md`. Код — `backend/app/services/org_limits.py`.

## Зачем

Критерий шага: **один клиент не кладёт API остальным.** До этого лимит частоты
считался по адресу посетителя (`app/api/guards.py`), и это правильно для
публичных ручек (вход, письма, приглашения), но не для рабочих:

* за одним офисным NAT сидит вся смена — клиент с сотней людей получал бы тот
  же потолок, что и клиент с пятью;
* клиент, разогнавший скрипт, занимал бы общий API — соседи по платформе
  чувствовали бы это как «приложение тормозит».

Поэтому рабочая частота считается **по организации**, а объём медиа ограничен
**квотой тарифа**.

## Что именно ограничено

| Тариф | Запросов в минуту на организацию | Медиа в базе |
| --- | --- | --- |
| Пробный (`trial`) | 300 | 200 МБ |
| Начало (`start`) | 600 | 1 ГБ |
| Бизнес (`business`) | 1200 | 5 ГБ |
| Сеть (`network`) | 2400 | 20 ГБ |

Цифры живут в `billing.PLANS` (`api_rpm`, `storage_mb`) — там же, где места и
подразделения. Тариф — это одна таблица, а не набор констант по разным местам:
правка цены и правка лимита должны попадать в один дифф.

300 запросов в минуту — это 5 в секунду на всю организацию. Активный экран
мини-аппа шлёт единицы; 300 — запас на смену из десяти человек, обновляющих
табель одновременно. Потолок тарифа выше в 2–8 раз: он для интеграций и
экспорта, а не для того, чтобы «просто работало».

## Как это работает

* **Где проверяется.** В зависимостях `deps.current_user` и
  `deps.current_employee`: организация известна только после аутентификации.
  В middleware её пришлось бы разбирать второй раз (подпись `initData` или
  сессию в базе) — двойная работа и второй источник правды о том, кто пришёл.
* **Один запрос — одно списание.** Флаг `org_limits.begin_request()` ставится
  middleware'ом `main.tenant_scope` в начале запроса; `enforce_rate` ставит
  «уже считал». Без этого пользователь и сотрудник в одном запросе списывали
  бы две единицы, и фактический лимит был бы вдвое ниже обещанного.
* **Кэш тарифа — 60 секунд** (`plan_code`). Поле меняется раз в месяц, лишний
  `SELECT` на каждом запросе не нужен. После оплаты счёта (`billing.mark_paid`)
  кэш сбрасывается явно — иначе клиент минуту жил бы со старым потолком и
  получал `429`, за который уже заплатил.
* **Недоступная база — не отказ.** Если тариф прочитать не удалось, работает
  `FALLBACK_RPM = 300` (потолок пробного). Лимит защищает от перегрузки и не
  должен сам становиться отказом.
* **Ответ `429`** содержит `Retry-After` и `X-RateLimit-Limit` /
  `X-RateLimit-Remaining` / `X-RateLimit-Reset`, тело —
  `{"detail": "org_rate_limited:<секунды>"}`. Клиент видит ограничение тарифа,
  а не «что-то пошло не так».
* **Квота хранилища** проверяется в `hr_media.store_bytes` **до** вставки блоба:
  отказ после `INSERT` всё равно оставил бы запись и счётчик. Превышение —
  `MediaError("storage_full")`, наружу `413` (это не битый файл, а граница
  квоты).

## Чего сознательно нет

* **Общего счётчика между репликами.** Счётчики в памяти процесса, как и у
  лимитов периметра: API — один процесс. При горизонтальном масштабировании
  потолок станет «на реплику»; честный общий счёт — Redis или таблица — идёт
  вместе с масштабированием, а не отдельным полурешением.
* **Лимита на публичные ручки по организации** — там организации ещё нет.
  Их по-прежнему закрывает `guards.RateLimitMiddleware` по адресу и общему
  счётчику контура.
* **Отдельной квоты на «тяжёлые» операции** (отчёты, экспорт): таких ручек,
  которые заметно дороже остальных, в продукте пока нет. Когда появятся
  (например, ИИ-разбор смен), квота добавляется сюда же — по тому же принципу
  «тариф задаёт границу».

## Как проверить руками

```bash
# 1. Лимит отключён для нагрузочной пробы:
ORG_QUOTA_OFF=1 ./.venv/Scripts/python.exe -m pytest tests/test_org_limits.py -q

# 2. Тесты шага:
./.venv/Scripts/python.exe -m pytest tests/test_org_limits.py -q
```

В тестах счётчики сбрасываются autouse-фикстурой `tests/conftest.py` — иначе
десятки тестов одной организации упирались бы в потолок тарифа, и падение
зависело бы от порядка файлов.

## Что видит клиент

Коды переводятся в `humanizeApiError` (`frontend/src/api/client.ts`), а не
показываются как есть: `org_rate_limited:<с>` → «Тариф упёрся в лимит
запросов — подожди N с», `storage_full` → «Место для фото по тарифу
закончилось». Код без перевода читается человеком как поломка.

## Если клиент упёрся

1. `429` с `org_rate_limited` — смотреть тариф организации в
   `/api/platform/orgs`; если клиент на пробном, предложить тариф выше.
2. `413 storage_full` — медиа организации заняли потолок. Решение — тариф выше
   либо чистка старых фото (фотоотчёты живут в `media_blobs`).
