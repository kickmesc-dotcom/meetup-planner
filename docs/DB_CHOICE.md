## 2. При чём тут лимиты

При 10 МБ любой тариф вмещает проект с запасом в десятки раз, включая
бесплатный Neon (0.5 ГБ). Поэтому решение определяется не объёмом, а двумя
другими свойствами:

1. **Заснет ли база.** В коде уже живут следы проблемы: `scheduler.py` хранит
   комментарий «HOTFIX 2026-06-12: 5мин→12ч. Neon free-tier суспендится после
   5мин», а целые куски логики (частоты job'ов, «не будить Neon», экономия
   SELECT'ов) существуют ради бюджета запросов. Платный инстанс Amvera спит
   ровно никогда — это снимает целый класс отказов и позволяет вернуть
   нормальные интервалы.
2. **Где лежат данные.** Neon — EU (`eu-central-1`), Amvera — Варшава. Для
   проекта, который переехал на Amvera под РКН, второе выглядит логичнее.

Точные цены и объёмы БД Amvera публично подтвердить не удалось
(`docs.amvera.ru` в момент проверки не отвечал) — они видны в консоли, и раз
инстанс уже оплачен, вопрос не в деньгах, а в том, чем вы платите за это
удобство.

## 3. Сравнение по существу

| | Neon (как сейчас) | БД Amvera (оплачена) |
|---|---|---|
| Засыпание | есть на free-tier (следы в коде) | нет |
| Латентность из контейнера | внешняя сеть, EU | вероятно ближе (в одном облаке) |
| Локация данных | EU | РФ-облако |
| Бэкапы / PITR | Neon branches | по тарифу Amvera — проверить в консоли |
| Единая точка отказа | бот (Amvera) → внешняя БД | всё у одного провайдера: упал Amvera — встало всё |
| Стоимость | 0 или подписка | уже платится |
| Что уже подстроено под неё | весь код (частоты, бюджет запросов) | ничего |

**Рекомендация.** При 10 МБ переносить данные дёшево в любую сторону, поэтому
идеальная конфигурация — не «или-или», а **одна рабочая база и один холодный
резерв**: рабочий указать в `DATABASE_URL` у обоих хостов, второй не удалять,
а пометить датой заморозки (переключение в любую сторону — это правка одной
переменной, см. раздел 5). Если цель — убрать засыпание и уехать в РФ,
переезжайте на Amvera; если цель — не трогать работающее, гасите оплаченный
инстанс или оставляйте его резервом.

## 4. План переноса (когда решите)

1. **Снять дамп боевой базы** — это и есть давно висящий пункт 0.4 спеки:
   ```
   pg_dump --no-owner --no-acl --format=custom "$DATABASE_URL_NEON" > meetup-$(date +%F).dump
   ```
   Проверить размер дампа: он должен быть того же порядка, что 10 МБ.
2. **Подготовить приёмник**: создать базу и пользователя в Amvera, собрать DSN.
3. **Прогнать миграции вручную** из локального venv (в контейнере это же делает
   `CMD`, но лучше увидеть ошибку заранее):
   ```
   DATABASE_URL=<amvera-dsn> backend/.venv/Scripts/python.exe -m alembic upgrade head
   ```
4. **Залить данные**: `pg_restore --no-owner --no-acl -d <amvera-dsn> meetup-….dump`
   (для `--format=custom`), либо `psql <DSN> < dump.sql` для plain-дампа.
5. **Переключить переменные и перезапустить**: `DATABASE_URL` меняется в
   **обоих** хостах (Amvera и HF) — иначе они разъедутся и половина данных
   уйдёт в одну базу, половина в другую. После рестарта проверить:
   ```
   backend/.venv/Scripts/python.exe tools/check-hosts.py
   ```
   Ожидаемо: `db.provider = amvera`, `db.alembic_version = 0021_game_media_posts`,
   `code.alembic_head = 0021_game_media_posts`.
6. **Пометить Neon замороженным** (например, добавить в его название дату
   `frozen 2026-09-29`) — вернуться к нему можно тем же способом шага 5.
7. Схему дальше синхронизировать только «вперёд»: новые миграции приезжают из
   кода, контейнер применяет их на старте. Обратный переезд на отставшую базу
   потребует снова `upgrade head`.

Если нужно, чтобы откат был мгновенным и без потери свежих записей, держите базы
синхронными через периодический `pg_dump` + `pg_restore` (данных на 10 МБ, это
секунды) — но это уже отдельная задача, и её стоит делать только если
переключения планируются регулярно.

## 5. Почему переключатели «никогда не срабатывали»

Файл `meetup-switch/` содержит два `.bat`, и они переключают **не то, что
нужно**: в них меняется только `TARGET` — URL вебхука Telegram, то есть какой
бэкенд обслуживает бота. Про базу там прямым текстом: «Code untouched; DB and
bot token shared with HF». Переключатель базы по вебхуку сработать не мог.

Глубже: `DATABASE_URL` читается из переменных окружения на старте контейнера, а
движок создаётся один раз и живёт в модульном синглтоне (`_engine` в
`app/db/base.py`). Никакой скрипт, лежащий на вашем компьютере, на это повлиять
не может — он может только поменять переменные у провайдера и попросить
перезапуск. Поэтому «переключение базы» — это всегда две правки env + рестарт,
а не один запущенный файл.

И была настоящая техническая мина, из-за которой даже правильное переключение
выглядело как «ничего не произошло»: SSL включался **безусловно** для любого
asyncpg-URL:

```python
if "asyncpg" in url:
    ctx = ssl.create_default_context()
    connect_args["ssl"] = ctx      # всегда, для любой базы
```

Это следствие жизни на Neon (он требует SSL). База, которая SSL не отдаёт,
на этом падала — контейнер не поднимался, а старый продолжал работать, что
внешне неотличимо от «переключатель не сработал». Исправлено: теперь режим SSL
явный — `DB_SSL=auto|require|disable` (по умолчанию `auto`: SSL включён везде,
кроме локальных хостов). При переезде на незнакомую managed-базу, если
подключение падает, достаточно поставить `DB_SSL=disable`.

## 6. Как переключаться теперь

1. Проверить кандидатов и узнать, что где живёт:
   ```
   backend/.venv/Scripts/python.exe tools/check-hosts.py
   ```
   Каждый хост сам сообщает свою базу (`db.provider`, `db.host`,
   `db.alembic_version`) и ревизию кода — без консоли и без SSH.
2. Поменять `DATABASE_URL` у обоих хостов (HF — в Settings → Variables, Amvera —
   в переменных окружения проекта), при необходимости `DB_SSL`.
3. Перезапустить оба, снова прогнать `tools/check-hosts.py` и убедиться, что
   `db.host` у них совпадает, а `db.alembic_version` равен `code.alembic_head`.

Скрипт `meetup-switch` стоит переименовать (он про канал/вебхук, а не про базу) —
иначе он будет и дальше обещать не то, что делает.
