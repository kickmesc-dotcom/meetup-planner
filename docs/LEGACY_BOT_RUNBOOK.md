# Старый бот рядом с новым: что поднять и что для этого нужно

Документ отвечает на два вопроса: **почему старый бот сейчас не открывается** и
**как поднять его отдельно**, не вытесняя новый. Написан 31.10.2026, после
проверки живых хостов.

## 1. Почему он не работает сейчас

Две независимые причины, обе — следствие того, что мы переиспользовали его же
площадки.

**Фронтенд старого приложения отдаёт 404.** Старый мини-апп жил на Hugging Face
Space `fryesw/meetup-planner-backend`: тот Space собирал Docker-образ и отдавал
и API, и статику фронтенда с корня. При переезде мы выложили на этот Space
**только бэкенд** (`tools/deploy-hf.py` копирует `app/`, `alembic/`,
`pyproject.toml`), и корень `/` стал отвечать `404 {"detail":"Not Found"}`.
Проверено: `/healthz` — 200, `/api/meta` — 200, `/` — 404. Для человека это и
есть «приложение недоступно»: он открывает мини-апп и видит ошибку.

**Ошибка авторизации — второе следствие того же.** Старый мини-апп обращался к
`/api/*` того же Space, где теперь живёт **новый** бэкенд с другой схемой
аккаунтов (`0056_accounts`, `0057_invitations`, `0059_email_verification`).
Старый фронт присылает старый формат авторизации — новый бэкенд его не знает и
отвечает 401. Токен от старой версии в новом контуре недействителен, и это
правильно: пускать его значило бы открыть доступ к чужой схеме прав.

Вывод: старую версию нельзя «включить обратно» на тех же адресах. Ей нужны
**свои** хост, база и бот.

## 2. Правило: три отдельности

| Что | Обязательно своё | Почему |
|---|---|---|
| `BOT_TOKEN` | отдельный бот или отдельный токен | у одного токена один вебхук: последний `setWebhook` выигрывает, и версии будут молча выбивать друг друга |
| `DATABASE_URL` | отдельная база (или ветка Neon) | у старого кода head `0028`, у нового `0063`. Общая база означает, что `alembic upgrade head` одной версии ломает вторую, а данные двух схем перемешиваются |
| домен | отдельный | мини-апп открывается по URL из кнопки меню; один URL не может вести в две версии |

Если хотя бы одно из трёх общее — версии будут конфликтовать, и это не
«глюк», а прямое следствие архитектуры Telegram и Alembic.

## 3. Что поднимать и где

Рекомендую **Amvera** для бэкенда старой версии — по той же причине, по которой
туда переехал новый: с российского Amvera есть прямой доступ к `api.telegram.org`
(замерено: TLS 1.3, 88 мс), а у HF выход в Telegram висит на рукопожатии.

**Бэкенд (бот + API старой версии).**

1. Новый проект в Amvera, отдельный slug, например `meetup-legacy`.
2. Отдельный git-репозиторий проекта Amvera; источник — `meetup-planner-backend`
   из `C:\Users\fa1nt\meetup-planner` (там уже лежат `Dockerfile` и `amvera.yml`,
   порт 7860, `alembic upgrade head` выполняется на старте контейнера).
3. Отдельная база: новая база Neon или отдельная ветка. **Не** та, что у нового
   контура. Пустая база наполнится миграциями `0001…0028`.
4. Переменные окружения — ровно те, что ждёт старый код
   (`meetup-planner-backend/.env.example`):

   | Переменная | Значение |
   |---|---|
   | `BOT_TOKEN` | токен **старого** бота из BotFather |
   | `TG_WEBHOOK_SECRET` | новый случайный секрет (сгенерирую сам) |
   | `PUBLIC_BASE_URL` | домен нового проекта Amvera, например `https://meetup-legacy-<login>.waw0.amvera.tech` |
   | `MINI_APP_URL` | адрес старого фронтенда (см. ниже) |
   | `DATABASE_URL` | строка подключения **отдельной** базы |
   | `WHITELIST_TG_IDS`, `WHITELIST_NAMES` | кто имеет доступ в старой версии |
   | `CORS_ORIGINS` | адрес старого фронтенда |
   | `LOG_LEVEL` | `INFO` |

5. После сборки — `setWebhook` на `PUBLIC_BASE_URL/tg/webhook` с тем же
   `secret_token`. Выполняется скриптом, токен не печатается.

**Фронтенд старой версии.** Отдельный проект Cloudflare Pages (например
`meetup-legacy`), сборка из `C:\Users\fa1nt\meetup-planner\meetup-planner-main\frontend`.
Имя проекта Pages должно отличаться от `semitaskbot` — иначе выкладка старого
фронта затрёт новый. На время сборки адрес API старого фронта указывается на
домен проекта Amvera из шага 4.

**Кнопка меню старого бота** (BotFather → Bot Settings → Menu Button) — на URL
старого Pages-проекта. Новый бот (`@SemiTaskBot`) остаётся смотреть на
`https://semitaskbot.pages.dev/`, его кнопку не трогаем.

## 4. Какие креды нужны от вас

Положите их **файлом**, не в чат: `secrets/legacy.env` в корне рабочей папки
(каталог `secrets/` уже вне git). Формат — обычный `KEY=value`, по строке:

```dotenv
# 1. Токен СТАРОГО бота: BotFather → выберите старого бота → API Token.
BOT_TOKEN=

# 2. Строка подключения ОТДЕЛЬНОЙ базы (Neon: новый проект или ветка).
#    Формат: postgresql+asyncpg://user:pass@host/db?ssl=require
DATABASE_URL=

# 3. Токен Amvera API (тот же тип, что используется сейчас для деплоя нового
#    контура), чтобы я мог собрать и выложить проект без вашего участия.
AMVERA_TOKEN=
```

Что **не** нужно и я сделаю сам:

- `TG_WEBHOOK_SECRET` — сгенерирую случайный;
- домены Amvera/Pages — создаются при первом деплое;
- Cloudflare-токен для Pages — уже есть в `secrets/`, отдельный не нужен.

Чего делать **нельзя** (иначе старая версия снова «выбьет» новую): не давать
старой версии `BOT_TOKEN` нового бота, не указывать ей базу нового контура, не
деплоить старый фронт в Pages-проект `semitaskbot`.

## 5. Проверка после подъёма

Порядок тот же, что для нового контура, и каждая строка — обязательна:

1. `GET /healthz` → `200 {"status":"ok"}`.
2. `GET /api/meta` → head миграций `0028`, число маршрутов старого кода.
3. `POST /tg/webhook` с неверным секретом → `403` (эндпоинт живой, секрет
   проверяется).
4. `getWebhookInfo` → URL старого проекта, `pending_update_count: 0`,
   `last_error_message: null`.
5. `/start` старому боту → отвечает (это проверяет уже **исходящий** доступ к
   Telegram, тот самый, что сломан на HF).
6. Вход в старое приложение по старой учётке → открывается лента, а не 401.
7. Повторно `getWebhookInfo` нового бота — URL по-прежнему
   `…amvera.tech/tg/webhook`, `pending 0`. Это главный тест на то, что версии
   не подрались.

## 6. Стоимость и время

- Проект Amvera: тот же тариф, что у нового контура (второй контейнер).
- База: бесплатной ветки Neon достаточно — это архивная версия.
- Работы: около часа, из них половина — сборка контейнера и миграции `0001…0028`.

## 7. Что важнее помнить

Старая версия — **архив**, а не второй продукт. Её ценность в том, что она
показывает, «как было», и не мешает новому. Если однажды понадобится поднять её
снова после простоя: сначала база (миграции), потом бэкенд, потом вебхук,
и только в конце кнопка меню — в этом порядке ничего не выбьется.
