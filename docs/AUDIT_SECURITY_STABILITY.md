# Аудит устойчивости и безопасности SemiTaskBot

Дата: **26.10.2026**. Область: боевой контур (`backend/` + `frontend/` + выкладка
на Amvera / HF Space / Cloudflare Pages). Метод — чтение кода, перечисление
маршрутов из живого приложения, поведенческие пробы на боевых хостах и запрос
к базе уязвимостей (OSV). Каждая находка ниже помечена доказательством, а не
мнением.

Как читать приоритеты:

| Метка | Значение |
| --- | --- |

## 0. Что уже сделано правильно (чтобы не переделывать)

Проверено и замечаний не вызывает: проверка `initData` через HMAC с
`compare_digest` и сроком; хранение в базе только SHA-256 от токенов сессий и
ссылок доступа; токен ссылки показывается ровно один раз и вычищается из
адресной строки; аренда лидерства планировщика через `SELECT … FOR UPDATE` (один
писатель на общую базу); дедупликация повторных апдейтов Telegram и бюджет ответа
вебхука; проверка загружаемых фото по сигнатуре, а не по `Content-Type`;
публичные байты фото по HMAC-подписи, а не по токену бота; тенантский фильтр на
уровне ORM-сессии; админ-права берутся из БД, а не из заголовка клиента;
сервис-воркер не кэширует `/api/*`.

## P0 — правки в первую очередь

### S-1. CORS: любой сайт читает ответы API под credentials

**Доказательство (живая проба 26.10.2026, HF Space):**

```
$ curl -D - -o /dev/null -H "Origin: https://evil.example" .../healthz
access-control-allow-credentials: true
access-control-allow-origin: https://evil.example
access-control-expose-headers: *
```

Причина в коде: `app/main.py` передаёт в `CORSMiddleware`
`allow_origins=settings.cors_origin_list or ["*"]` вместе с
`allow_credentials=True`, а по умолчанию `CORS_ORIGINS="*"`. Это не «звёздочка в
ответе», а именно **зеркалирование любого Origin**: в Starlette при
`allow_all_origins and allow_credentials` заголовок подменяется на Origin
запроса (`starlette/middleware/cors.py`, строки 39–41 и 160–166). Предпросмотр
(`OPTIONS`) тоже отвечает `allow-origin: https://evil.example`.

Сейчас урон ограничен тем, что входы у нас на заголовках (`Authorization`,
`X-Access-Token`), а не на cookie: чужой сайт не может приложить чужой токен.
Но: (1) стоит добавить любую cookie-авторизацию — и это мгновенный захват
аккаунта; (2) браузер жертвы всё равно ходит на наш API по команде чужого сайта,
то есть нас используют как бесплатный бэкенд; (3) `expose-headers: *` отдаёт
чужому коду все заголовки ответа.

**Правка.** Белый список Origin собирается из конфигурации, а не из `*`:
адреса мини-аппа и приложения (`MINI_APP_URL`, `APP_PUBLIC_URL`), явный список из
`CORS_ORIGINS` плюс регулярка на превью-развёртывания Pages
(`https://*.semitaskbot.pages.dev`) и локальные `localhost`/`127.0.0.1` для
разработки. Если в `CORS_ORIGINS` всё-таки стоит `*` — credentials
принудительно выключаются, чтобы конфигурация не могла повторить эту дыру.
Тест: чужой Origin не получает `allow-origin`, свой — получает, предпросмотр
чужого Origin отклоняется.

### S-2. Нет ограничения на размер тела запроса

**Доказательство.** В `main.py` нет middleware размеров, в `app/api/routes_media.py`
лимит 8 МБ проверяется уже **после** `await upload.read()`
(`services/hr_media.py: store_upload`) — то есть после того, как тело целиком
принято и разложено `python-multipart` (мелкие части в память, крупные — во
временные файлы). Проба на боевом хосте с большим телом не делалась сознательно:
это и есть отказ в обслуживании.

Что происходит сейчас: `POST /api/media`, `POST /tg/webhook` и любая другая
ручка принимают тело произвольного размера. Контейнер на Amvera/HF с небольшим
диском и одним воркером: переполнение временного каталога или памяти — это
падение контура, а не «ошибка одного запроса».

**Правка.** ASGI-middleware, который (1) отклоняет запрос по `Content-Length`
сразу с `413`, (2) при отсутствии длины (chunked) считает байты в потоке и
обрывает чтение, превысившее лимит. Плюс защита в глубину в
`hr_media.store_upload`: чтение порциями с обрывом на превышении, чтобы 8-МБ
правило не зависело от middleware.

### S-3. Нет ограничения частоты на публичных ручках: перебор пароля и рассылка писем

**Доказательство.** Перечисление маршрутов живого приложения даёт 353 маршрута
`/api` и `/tg`; из них без зависимости авторизации — 16, и в их числе
`POST /api/auth/login`, `POST /api/auth/register`,
`POST /api/auth/password/reset/request`, `POST /api/auth/email/verify/request`.
Поиск по `backend/app` не находит ни одного ограничителя частоты (единственное
`429` — самодельный лимит вступления по приглашению). Пароли хешируются, но
перебор ничем не замедлен, а `reset/request` на каждый вызов шлёт письмо через
Resend/SMTP — то есть это ещё и платная рассылка по чужим адресам.

**Правка.** Лимитер в процессе (окно по IP и правилу): вход/регистрация —
20 за 5 минут, запросы писем (сброс, подтверждение адреса) — 5 за 15 минут,
загрузка фото — 60 за 5 минут. Ответ `429` + `Retry-After`, код
`rate_limited:<секунды>` — фронт показывает человеческий текст. Вебхук Telegram
не лимитируем: это законный трафик, а его вектор закрыт размером тела.

### S-4. TLS-сертификат базы не проверяется

**Доказательство.** `app/db/base.py`:

```python
ctx = ssl.create_default_context()
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE
```

Соединение с Postgres шифруется, но собеседник не аутентифицируется: кто встал
между контейнером и базой (провайдер, прокси, отравленный DNS), читает и
подменяет всё — пароли в запросах, токены, содержимое лент. Для базы с
персональными данными сотрудников это дыра, а не «настройка ради совместимости».

**Правка.** По умолчанию (режим `auto`) соединение проверяется
(`CERT_REQUIRED` + `check_hostname=True`). Если проверка не проходит из-за
сертификата (локальная/самоподписанная managed-база), приложение один раз
пробует подключиться с проверкой на старте и, только если сертификат действительно
невалиден, переходит в непроверенный режим **с громкой ошибкой в логе**. Явные
режимы остаются: `DB_SSL_VERIFY=require` (всегда проверять, падать) и
`DB_SSL_VERIFY=off` (никогда, для локальной базы).

### S-5. `/healthz` не проверяет базу: контейнер «здоров» при мёртвой БД

**Доказательство.** `main.py: healthz()` возвращает `{"status": "ok"}` без
единого обращения к БД. Оркестратор (и наш `tools/check-hosts.py`) считает
контейнер живым, пока процесс отвечает, — а все ручки в это время отдают 500.
Это ровно тот класс инцидентов, из-за которого контейнер уходил в
`RUNTIME_ERROR` (см. `docs/AMVERA_BUILD_DIAGNOSTIC.md`).

**Правка.** `/healthz` остаётся дешёвой проверкой живости, добавляется
`/readyz`: `SELECT 1` с таймаутом 2 с и честный `503` с причиной, если база
недоступна. Выкладка и проверка после неё смотрят на `/readyz`.

## P1 — правки во втором пакете

### S-6. Боевые зависимости с известными уязвимостями

**Доказательство.** Запрос к OSV (`api.osv.dev/v1/query`) по **пинам из
`backend/pyproject.toml`**, то есть по тому, что реально собирается в образ
(`Dockerfile: pip install .`):

| Пакет | Версия | Уязвимостей | Что важно из списка | Минимум для закрытия |
| --- | --- | --- | --- | --- |
| `python-multipart` | 0.0.17 | 16 | DoS через деформацию boundary multipart; DoS на заголовках части; произвольная запись файла при нестандартной конфигурации; отрицательный `Content-Length` буферизует тело целиком | **0.0.31** |
| `starlette` | 0.41.3 | 14 | DoS на больших multipart-формах (≥0.47.2); O(n²) на `Range` в `FileResponse` (≥0.49.1); отсутствие валидации `Host`, отравляющее `request.url.path` (≥1.0.1) | **1.3.1** |
| `aiohttp` | 3.10.11 | 74 | неограниченная очередь pipelined-запросов, позднее ограничение размера полей, CRLF в multipart, утечки cookie-атрибутов | **3.14.4** |

Первые два — это ровно наш случай: мы принимаем `multipart/form-data`
(фотоотчёты) и отдаём файлы. `starlette` поднимается вместе с `fastapi`
(0.115.6 держит `starlette<0.42`), поэтому правка — это согласованный подъём
трёх пакетов: `fastapi` → версия, разрешающая `starlette ≥1.3.1`,
`starlette` → ≥1.3.1, `python-multipart` → ≥0.0.31, `aiohttp` → ≥3.14.4.
Обязательна проверка полным набором тестов; при несовместимости — фиксируем
`fastapi` минимальной версией, которая пропускает исправленный `starlette`.

### S-7. У фронтенда нет CSP, а токен лежит в `localStorage`

**Доказательство.** `frontend/public/` не содержит `_headers` (в Cloudflare
Pages это единственный способ отдать заголовки безопасности), `index.html`
подключает только `https://telegram.org/js/telegram-web-app.js`.
`frontend/src/api/client.ts` хранит сессию (`semitask.session_token`) и ссылку
доступа (`semitask.access_token`) в `localStorage`. То есть одна инъекция
скрипта (рекламный скрипт, кривое расширение, XSS в текстах из админки) отдаёт
аккаунт целиком — вместе с правами управляющего.

**Правка.** `frontend/public/_headers`: CSP (запрет внешних скриптов, кроме
Telegram-скрипта; `frame-ancestors` только для Telegram, иначе мини-апп перестанет
открываться в вебе), `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy`, HSTS. Никакого `X-Frame-Options`: он запрещает любые
iframe и сломает открытие мини-аппа внутри Telegram.

### S-8. SSRF через подписку на push

**Доказательство.** `app/api/routes_push.py`: `PushSubscribeIn.endpoint` —
строка от клиента (10…2000 символов), сохраняется как есть и позже передаётся в
`pywebpush`, который делает HTTP-запрос по этому адресу. Проверки схемы и хоста
нет. Аутентифицированный сотрудник заводит подписку на
`http://169.254.169.254/…` или на внутренний адрес хостинга — и заставляет
сервер ходить туда (метаданные облака, внутренние сервисы), с нашими
заголовками и нашим исходящим IP.

**Правка.** Разрешаем только `https`, публичные хосты (никаких IP-литералов,
`localhost`, `.local`, `169.254.*`, `10.*`, `172.16-31.*`, `192.168.*`,
`[::1]`) и известные пуши-сервисы. Отказ — код `push_endpoint_rejected`.

### S-9. Проверка прав в админ-ручках держится на дисциплине

**Доказательство.** В `routes_admin.py` 145 маршрутов, и доступ проверяется
императивно внутри тела (`_ensure_admin(user)`, `_diag_token_ok(request)`).
Единого «предохранителя» на уровне роутера нет, а список публичных маршрутов
нигде не зафиксирован: одна забытая строка — и новая ручка открыта всему
интернету. Ручной разбор кода уже находил такие места в других проектах.

**Правка.** Тест-инвариант: у каждого маршрута под `/api/admin` есть зависимость
авторизации, а список маршрутов без авторизации **зафиксирован в тесте**
(16 записей с обоснованием). Новая публичная ручка без правки списка — красный
тест.

## P2 — третий пакет и план на потом

### S-10. Ссылка на календарь: 64 бита HMAC, бессрочная, без отзыва

`services/ical.py`: `HMAC(tg_webhook_secret, user_id)[:16]` — 64 бита, вечная,
отозвать нельзя иначе как сменой секрета вебхука (а это ломает и вебхук, и все
остальные iCal-ссылки). Ссылка попадает в логи почтовых клиентов и прокси.
Правка: новые ссылки — 128 бит (`[:32]`), старые принимаются (совместимость
уже выданных подписок), ротация — через смену секрета с записью в документации.

### S-11. Медиа-ссылки вечные и подписаны ключом бота по умолчанию

`services/hr_media.py`: ключ подписи — `settings.bot_token` организации по
умолчанию, срок не задан. Фотоотчёт со смены доступен по ссылке навсегда и
любому, у кого она есть, в том числе после увольнения сотрудника. Правка на
будущее: срок годности в подписи (`?s=…&e=<unix>`) и ключ на организацию; в
отчёт — как принятый риск с датой.

### S-12. Публичные ручки, отдающие лишнее

`GET /api/avatar/{user_id}` — перечисление пользователей и их аватары;
`GET /api/meta`, `GET /api/meta/net` — провайдер базы, версия сервера, head
миграций, отпечаток кода (хост замаскирован, но версия СУБД остаётся).
Правка: у `meta` оставить только то, что нужно фронту, версию СУБД убрать; у
аватара — подпись, как у медиа.

### S-13. Сравнение секретов не constant-time

`services/org_bots.py`: `cfg.webhook_secret == secret` и `cfg.token == token`.
Практически неизмеримо по сети, но правка бесплатная: `hmac.compare_digest`.

### S-14. Оба хоста делают `alembic upgrade head` на одной базе

`Dockerfile: CMD ["sh","-c","alembic upgrade head && uvicorn …"]`, а база одна
на Amvera и HF. Одновременный перезапуск двух контейнеров — гонка двух DDL за
одну схему. Правка: обёртка миграций, берущая advisory-lock Postgres
(`pg_advisory_lock`), чтобы второй контейнер ждал, а не наступал.

## Что сделано (по факту, а не по плану)

### Пакет 6 — S-1b: широкая регулярка CORS из переменных среды, выложено 26.10.2026

Это уточнение к S-1, найденное при его же доработке — и оно важнее исходной
находки. Правка S-1 (белый список вместо `*`) была верна в коде, но **одна
забытая переменная окружения обнуляла её целиком** — и только на боевом хосте:

```
# HF, 26.10.2026, после выкладки пакета 1
$ curl -D - -o /dev/null -H "Origin: https://evil.example.com" .../api/meta
access-control-allow-origin: https://evil.example.com   ← отражение чужого сайта
access-control-allow-credentials: true

# Amvera, тот же код и тот же момент
(заголовка access-control-allow-origin нет вообще)      ← а тут правильно
```

**Как найдено.** `/api/meta` на обоих хостах показывал один и тот же отпечаток
кода, то есть дело не в «отставшей сборке». Разница оставалась только в
окружении, и её удалось воспроизвести локально: с `CORS_ORIGINS` списком и
встроенной регуляркой чужой Origin получает отказ (как на Amvera), а с
`CORS_ORIGIN_REGEX=https://.*` — `allow-origin` с отражением и
`allow-credentials: true` (как на HF). Вывод: в Space с прошлых запусков лежала
широкая `CORS_ORIGIN_REGEX`, а `tools/deploy-hf.py` её не трогал — в списке
выгружаемых ключей её просто не было.

**Правка в коде (главная, потому что она не зависит от чужой переменной).**
Регулярка, пришедшая из среды, проверяется на «ловушках»
(`config.CORS_ORIGIN_CANARIES`): если она пускает `evil.example.com` — она
отбрасывается и берётся встроенный безопасный шаблон. Проверяются обе
семантики сверки, `fullmatch` и `match`: версии Starlette разные, и обрезанный
шаблон вида `https://evil\.example\.co` ловится только вторым. Невалидная
регулярка тоже считается опасной, а не «непонятной».

**Правка в выкладке.** `CORS_ORIGIN_REGEX` добавлен в список ключей
`tools/deploy-hf.py`, и при отсутствии значения у владельца уезжает безопасное
по умолчанию — то есть широкая переменная в Space больше не может «зависнуть»
незамеченной.

**Правка в диагностике.** `/api/meta/net` (под секретом) теперь отдаёт
эффективную политику CORS: `origins`, `credentials`, `regex`, `regex_rejected`.
Вопрос «почему на хосте CORS шире, чем в коде» теперь задаётся хосту, а не
выясняется догадками, — именно этой информации не хватало при первом разборе.

#### Проверка после выкладки 27.10: часть отражения — не наша, а края HF

Пакет 6 выложен на оба хоста, и пробы принесли важное уточнение — привожу как
есть, вместе с тем, что оно меняет в выводах.

| Проба (27.10.2026) | HF | Amvera (тот же код, тот же commit) |
| --- | --- | --- |
| `GET /api/meta`, `Origin: https://evil.example.com` | `allow-origin: https://evil.example.com`, `credentials: true` | заголовка нет |
| `GET /api/meta`, свой домен и превью Pages | отражение | `allow-origin` ровно свой домен / превью |
| `/api/meta/net` (под секретом) | `origins: [pages.dev]`, `regex` — встроенный безопасный, `regex_rejected: false` | то же самое |
| `OPTIONS /nope-404` с `Access-Control-Request-Method: DELETE` | `200` + `allow-origin` + **`allow-methods: DELETE`** (эхо запрошенного метода) | `400` (Origin не разрешён) |
| Лог контейнера HF в тот же момент | `GET /nope-404 404`, **строки про `OPTIONS` нет вообще** | — |

Вывод по доказательствам: на HF заголовки CORS ставит **край платформы**, а не
наше приложение. Три независимых признака: (1) `OPTIONS` до контейнера не
доходит — в логе его нет, а клиент получает `200`; (2) `allow-methods`
возвращает *эхо* запрошенного метода, тогда как Starlette при `allow_methods=["*"]`
перечисляет все методы списком; (3) `Vary` в ответе края трёхсоставный
(`origin, access-control-request-method, access-control-request-headers`),
а Starlette пишет только `Origin`. Плюс главное: эффективная политика,
которую приложение само показывает в `/api/meta/net`, — безопасная, и на
Amvera с тем же кодом отражения нет.

Что это значит практически:

- правка S-1b остаётся правильной и нужной (забытая широкая переменная
  действительно обнуляла бы белый список, и теперь такое значение отбрасывается
  и видно в диагностике), но **первопричина отражения на HF была не в ней**;
- в коде это не чинится: край отвечает на preflight сам, до приложения. Варианты
  — либо принять как ограничение площадки, либо поставить API за Cloudflare
  (там заголовками управляем мы, и `deploy/cloudflare/worker.js` для этого уже
  есть), если понадобится строгий CORS;
- на безопасность данных это не влияет: вход в API идёт по `Authorization`
  Bearer и Telegram `initData`, cookie-сессии не используются, поэтому чужой
  сайт с отражённым Origin не получает доступа к данным без токена. Отражение
  `credentials: true` опасно именно для cookie-аутентификации, которой здесь нет.
  Записано как ограничение, а не как «закрыто».

**Про `aiohttp`: как погоня за патчами упёрлась в 0,5 ГБ.** Итог тот же, что и у

`aiohttp` нельзя поднять в одиночку: его версию ограничивает `aiogram`
(`aiohttp<3.11` до 3.16, `<3.12` до 3.20, `<3.14` до 3.28, `<3.15` только с 3.29).
Первый прогон поднял одну `aiohttp` — и HF Space встал с `ResolutionImpossible`,

проверяется установкой в чистое окружение — тесты бегут на том, что уже стоит, и
конфликт версий в них не виден; (2) у хоста есть потолок памяти, и его надо
знать до того, как выбирать версии.

**Про `fastapi`/`starlette` — сознательно не подняли в этом пакете.** Аудит
оказался верен: `starlette 0.41.3` тянет 14 advisories, и они закрываются только
вместе с мажорным `starlette 1.3.1+`. Попытка поднять показала **регрессию в
проде**, а не в тестах: в FastAPI/Starlette 1.x включённые роутеры больше не
разворачиваются в плоский список, `app.routes` отдаёт 33 объекта вместо 359, и

слоями: multipart-DoS закрыт лимитом размера тела (S-2), а `Range`/`FileResponse`

| Находка | Правка | Проверка |

| S-11 медиа-ссылки без срока | подпись стала `срок.hmac`, срок внутри подписи — его нельзя продлить правкой адреса; по умолчанию 90 дней (`MEDIA_LINK_TTL_DAYS`), округление ВНИЗ до суток, чтобы адрес не менялся каждый час | `tests/test_media_link_expiry.py` (13 проверок): живая ссылка проходит, просроченная — нет, подделка срока — нет, подпись привязана к `kind` и id, срок в URL присутствует |
| Старые ссылки (без срока) | принимаются до `MEDIA_LEGACY_SIG_UNTIL` (сейчас 31.12.2026) и о каждой пишется `media.legacy_signature_used` — видно, если они ещё ходят | тесты на «принимается до даты» и «отказывается после»; окно закрывается само, без второго выпуска кода |

Почему срок именно такой. Прокси на краю Cloudflare кэширует фото по полному адресу, вместе с подписью (`frontend/functions/api/media/[[path]].ts`), и там же записано «ссылка неизменна». Срок «от текущего момента» менял бы адрес постоянно и убил бы этот кэш — фото в РФ поехали бы из контейнера заново каждый раз. Поэтому сутки — единица стабильности адреса, а 90 дней — граница жизни утёкшей ссылки.

Найденное попутно (написали тест — он и поймал): `verify` сравнивал подписи через `compare_digest` по `str`, а тот падает на не-ASCII — ссылка с кириллицей в параметре давала бы `500` вместо `403`. Сравнение переведено на байты; та же ошибка ранее ловилась в секретах бота (S-13).

Осталось в этой находке: **ключ на организацию и отзыв ссылок** — сейчас ключ один (токен бота), поэтому «отозвать только чужой доступ» всё ещё нельзя, только «поменять ключ для всех». Это отдельная задача: `verify` должен знать организацию до проверки подписи, то есть читать блоб/фото из БД раньше (плюс у блобов и фото есть `org_id`, схему менять не нужно).
