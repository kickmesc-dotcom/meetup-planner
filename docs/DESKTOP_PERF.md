# Почему широкий экран «тормозит» и что с этим делать

Замеры 29.10.2026, с рабочей машины (Россия), без VPN. Все числа — реальные
ответы живых хостов, а не оценки «на глаз».

## Что измерено

| Что | Значение |
| --- | --- |
| `GET /api/meta` (Amvera, 3 прогона) | 0,90 с · 0,66 с · 0,75 с |
| `GET /healthz` (Amvera) | 0,52 с · 0,65 с |
| `GET /` (Cloudflare Pages) | 1,05 с |
| JS-бандл | 961 кБ (286 кБ gzip) одним файлом |
| Статика `/assets/*` | `immutable`, 1 год — повторно не скачивается |
| Кол-во запросов при открытии | 6 верхнеуровневых (`me`, `users`, `hr-employee`, `hr-tasks`, `org-setup`, `ui-prefs`) + запросы экрана и правого рельса |
| RTT до Amvera | ~0,3 с (Польша, `waw`) |

## Где на самом деле уходит время

1. **Каждый запрос — за границу.** Полсекунды-секунда на `/healthz`, который
   вообще ничего не считает. Это сеть плюс холодный/слабый контейнер, а не
   «тяжёлые» запросы. Экран, которому нужно четыре запроса подряд, не может
   быть быстрее 2–3 секунд при таком фундаменте.
2. **Запросы идут крест-накрест.** Приложение на `semitaskbot.pages.dev`,
   API на `*.amvera.tech`. Заголовок `Authorization` делает запрос
   «непростым», поэтому **каждый новый эндпоинт стоит два круга**: `OPTIONS`
   (preflight) + сам запрос. Starlette кэширует preflight на 10 минут
   (`Access-Control-Max-Age` по умолчанию 600), но первая загрузка платит
   дважды за каждый адрес.
3. **Один бандл на всё приложение.** 286 кБ gzip — это и админка на 4700
   строк маршрутов, и отчёты, и вся legacy-часть. Скачивается и парсится
   раньше, чем человек увидит ленту.
4. **Контейнер один и слабый.** 0,5 ГБ RAM, общий CPU, один инстанс. Пока
   идёт сборка/прогрев модели перевода, все запросы стоят в очереди.
5. **Ничего не кэшируется между визитами.** `staleTime` живёт в памяти
   вкладки: перезагрузка страницы = заново все шесть запросов.
6. **Холодный старт.** После простоя контейнер поднимается десятки секунд;
   внешний cron `healthz` помогает, но не отменяет RTT.

Логи Amvera подтверждают третий пункт косвенно: в момент открытия широкой
версии в логах идут пачки `OPTIONS …/api/me` — по одному на каждый повторный
заход, и часть из них отвечает `400` на чужой Origin (это нормальная защита
CORS, но каждый такой отказ — потраченный круг).

## Варианты: от бесплатных к платным

### 1. Один запрос вместо шести: `/api/bootstrap` — **сделано 29.10.2026**

Сервер отдаёт `me + users + employee + tasks + org-setup + ui-prefs` одним
ответом (`backend/app/api/routes_bootstrap.py`), фронт раскладывает его по
кешу react-query под обычными ключами (`frontend/src/api/bootstrap.ts`).

Замер на живом Amvera после выкладки, три подряд прогона, запросы без токена
(оба пути отвечают 401 — то есть меряется ровно сеть, preflight и middleware,
без запросов к базе):

| Как | Кругов | Секунды (3 прогона) |
| --- | --- | --- |
| Шесть ручек | 12 (6 × OPTIONS + GET) | 6,70 · 6,69 · 6,69 |
| Одна ручка | 2 | 1,15 · 1,16 · 1,16 |

Что это значит честно. Сумма последовательная, а браузер тянет запросы
частично параллельно — поэтому выигрыш «в моменте» меньше, чем 6,7 против
1,15. Но каждый из шести адресов всё равно платит свой preflight, а контейнер
0,5 ГБ обслуживает их по очереди: убирается не одно слагаемое, а пять.
Отдельно замечено в первом прогоне: `GET /api/me/employee` один раз ответил за
3,1 с — то есть в живом приложении рядом с сетью стоят ещё и очереди, и
холодный старт.

- **Выгода:** 12 кругов → 2. Плюс уходит дубль работы в базе: шесть ручек
  читали одни и те же настройки организации.
- **Цена:** как и предполагалось — одна ручка и раскладка по кешу. Через
  месяц-два эксплуатации станет видно, не пора ли часть полей вынести из
  старта в отдельный запрос (кеш и инвалидация не бесплатны).
- **Риск, который был и остался:** если ручка недоступна (человек без
  членства в организации, старый сервер без неё), App включает шесть обычных
  запросов — деградация до вчерашнего поведения плюс один лишний запрос.
  Поэтому у ручки `retry: false`: падение должно сразу отдавать управление,
  а не тянуть скелетон на трёх попытках.

### 2. API через свой домен (бесплатно на Cloudflare, ~2 дня)

Worker на `semitaskbot.pages.dev/api/*` проксирует в Amvera. Браузер видит
**тот же origin**.

- **Выгода:** исчезает preflight целиком (минус один круг на каждый адрес);
  один домен вместо двух — меньше проблем с блокировками и VPN; можно
  включить edge-кэш для GET, которые не зависят от человека (настройки
  организации, отделы, стандарты, ссылки).
- **Цена:** воркер и маршрут, проброс заголовков и тела, аккуратные правила
  «что кэшировать» (`Cache-Control: private` для всего, что про человека).
- **Риск:** средний: ошибка в правилах кэша = чужие данные в чужом кэше.
  Поэтому кэш только для явно перечисленных публичных GET.

### 3. Кэш запросов между визитами (бесплатно, ~2 дня)

`persistQueryClient` в `localStorage` с версией и коротким TTL: повторный вход
рисует экран из памяти и обновляет в фоне.

- **Выгода:** второй и последующие заходы выглядят мгновенными — а сотрудник
  открывает приложение по десять раз за смену.
- **Цена:** версионирование кэша, очистка при выходе, TTL, чтобы вчерашние
  поручения не выглядели сегодняшними.
- **Риск:** выше предыдущих: личные данные лежат в браузере. На общем
  устройстве это утечка. Либо не кэшировать ничего персонального, либо
  кэшировать только справочники (`org-setup`, `departments`, `standards`).

### 4. Разрезать бандл (бесплатно, ~1 день)

`React.lazy` + `Suspense` для админки, отчётов и табеля: сотрудник не качает
код управления.

- **Выгода:** минус примерно 30–40 % начального JS; на медленном канале это
  заметно, на быстром — почти нет.
- **Цена:** точки разделения, скелетоны при подгрузке чанка (иначе экран
  мигает пустотой).
- **Риск:** низкий. Главное — не разрезать так, чтобы первый экран тянул три
  чанка.

### 5. Прогрев и «не спать» (бесплатно, ~1 час)

Cron каждые 5 минут дергает `/healthz` и один лёгкий GET.

- **Выгода:** убирает холодные старты (десятки секунд после простоя).
- **Цена:** почти нулевая.
- **Риск:** нет. Но RTT и слабый CPU это не лечит — только пики.

### 6. Ближе к людям (от ~300–500 ₽/мес, ~3 дня)

Тот же контейнер на хостинге с европейским/российским регионом рядом с
пользователями (или вторая реплика Amvera).

- **Выгода:** RTT 0,3 с → 0,05–0,1 с; на шести запросах это уже секунды.
- **Цена:** деньги и переезд (переменные, вебхук, домен).
- **Риск:** средний: бот и планировщик должны переехать вместе с API, иначе
  вебхук останется на старом хосте.

### 7. Читающие ручки на edge, Cloudflare Workers + D1 (средняя работа, ~1–2 недели)

Часть GET (лента, график, справочники) отдаётся из edge-хранилища, запись —
по-прежнему в Postgres.

- **Выгода:** 20–50 мс на чтение где угодно, без холодных стартов; это
  единственный вариант, который убирает проблему «медленно в любой стране».
- **Цена:** большая: вторая модель данных, синхронизация, миграции.
- **Риск:** высокий. Имеет смысл только если продукт выйдет за пределы одной
  команды.

### 8. Платный тариф Amvera / Neon (от ~500 ₽/мес, ~1 час)

- **Выгода:** больше CPU/RAM, меньше очередей; Neon — быстрее отдача запросов.
- **Цена:** деньги, без правок кода.
- **Риск:** низкий, но и выигрыш ограничен: полсекунды сетевого плеча
  останутся.

## Что рекомендую по порядку

1. **№1 (bootstrap) + №5 (прогрев)** — бесплатно, снимают самые дорогие круги
   и пики.
2. **№2 (свой домен через Worker)** — бесплатно, убирает preflight и даёт
   место для аккуратного edge-кэша.
3. **№4 (разрезать бандл)** — бесплатно, доделывает первую загрузку.
4. Только потом деньги: **№6**, если первых трёх не хватит.

Пункт 3 (кэш в браузере) сознательно ставлю ниже: выигрыш большой, но это
личные данные сотрудника на его устройстве — решение владельца, а не
техническое улучшение «по умолчанию».
