# Вход, роли и место группового чата

Дата: **31.10.2026**. Документ отвечает на три вопроса, которые возникли при
запуске живого пилота:

1. зачем боту чат, если продукт теперь живёт в приложении;
2. кто получает права редактора и почему их нельзя выдавать из переменных
   окружения;
3. как человек входит без Telegram и что будет со связкой двух аккаунтов.

---

## 1. Три способа войти — один пользователь

| Способ | Как работает | Когда используется |
|---|---|---|
| **Telegram Mini App** | клиент присылает `initData`, подписанный токеном бота; сервер проверяет HMAC | основной путь: сотрудник открывает бота и нажимает кнопку приложения |
| **Ссылка на веб-версию** | `?access=sweb_…`, в базе лежит только SHA-256, срок 30 дней, отзывается | настольный браузер, закладка; выпускается из бота и профиля |
| **Почта и пароль** | `/api/auth/register`, `/api/auth/login`, подтверждение почты, сброс пароля | клиент без Telegram: наёмный офис, управляющий, аудит |

Все три ведут в одну таблицу `users`. У пользователя из Telegram заполнен
`telegram_id`, у пользователя по почте — `email` и `password_hash`. Оба поля
допускают `NULL`, поэтому один и тот же код (`ensure_employee`,
`require_admin`, все HR-ручки) обслуживает любой способ входа — права не
зависят от того, как человек вошёл.

Важная деталь регистрации: **аккаунт по почте сам по себе не даёт доступа к
данным**. `accounts.register` намеренно не создаёт ни сотрудника, ни членства
в организации — иначе человек молча оказался бы в первой организации базы.
Попасть внутрь можно только по приглашению: `InviteScreen` → `/api/orgs/join`.

## 2. Роли: два независимых слоя

### 2.1 Уровень доступа в организации (`org_members.role`)

| Значение | Что значит | HR-роль |
|---|---|---|
| `owner` | владелец организации: управляет всем, включая роли | `admin` |
| `manager` | управляющий: поручения, приёмка, отчёты | `aup` |
| `staff` | сотрудник | `employee` |

Это **данные**, а не конфигурация: строки живут в базе, выдаются приглашением
и меняются в интерфейсе (`routes_hr_ops_admin`).

### 2.2 Переменные окружения (`ADMIN_TG_IDS` + `BUILTIN_ADMIN_TG_IDS`)

До 31.10.2026 в `staff_tg_id_set` склеивались **два** списка —
`ADMIN_TG_IDS` и `WHITELIST_TG_IDS`, — и каждый, кого вписали в «список людей
проекта», автоматически получал кабинет управления. На проде это выглядело так:
`ADMIN_TG_IDS` и `WHITELIST_TG_IDS` были побайтово одинаковыми, админами были
все шестеро.

Как теперь:

* `staff_tg_id_set` = `ADMIN_TG_IDS` + встроенная пара `BUILTIN_ADMIN_TG_IDS`
  (`306733739`, `397594558` — владелец и соавтор);
* `WHITELIST_TG_IDS` больше не даёт **ничего**, кроме «человек известен сиду»;
* на боевом проекте `ADMIN_TG_IDS=306733739,397594558`, и в базе ровно два
  профиля с ролью `admin`.

Зачем env-список вообще остался: он работает **на пустой базе**. Если владелец
снимет себе роль в интерфейсе и что-то сломает, вернуть права будет нечем, если
права живут только в базе. Поэтому env-пара — это бутстрап продукта, а не
механизм выдачи прав клиентам.

**Правило на будущее:** ни одному клиенту, ни одной команде мы не прописываем
её Telegram-id в `ADMIN_TG_IDS`. Клиентский владелец получает `admin` из
`org_members.role='owner'`, и это единственный путь, который одинаково работает
для Telegram и для входа по почте.

### 2.3 Что видит сотрудник, а что руководитель

Интерфейс делит приложение на две зоны (и это же разделение проверяется на
сервере):

| Зона | Что внутри | Кому видно |
|---|---|---|
| «Все разделы» | спросить, материалы, ссылки, стандарты, журнал, передача смены, график, встречи, обратная связь | всем |
| «Руководителю» | команда, приёмка, отчёт смены | `aup` / `admin` |
| «Управление предприятием» | подразделения, чек-листы, роли, приглашения | `admin` |

Сотрудник не видит управленческих строк вообще — не «видит, но неактивные».

## 3. Групповой чат — необязательная функция

Раньше бот жил в рабочем чате, и чат был условием работы. Теперь наоборот:
сотрудник заходит в мини-апп и **сам выбирает команду**; группа нужна только для
анонсов и как «общий пул».

Что сделано, чтобы это стало правдой в коде:

| Ситуация | Поведение |
|---|---|
| `GROUP_CHAT_ID` не задан | штатный режим: `settings.group_chat_id = None`, групповые части пропускаются |
| чат указан, но Telegram отвечает `chat not found` | на старте один `getChat`, затем `group_chat.disabled` в логе и env-чат выключается до перезапуска |
| сеть/прокси подвели при проверке | чат **не** выключается: временный сбой не повод терять рабочий id |
| чат задан в `organizations.group_chat_id` (клиент со своим ботом) | не трогаем: он жив независимо от переменной по умолчанию |

Текущее состояние боевого контура: `GROUP_CHAT_ID=-1003588632778` отвечает
`400 Bad Request: chat not found` (бота вывели из группы или id устарел).
С 31.10.2026 это больше не ошибка старта: в логе одна строка
`group_chat.disabled`, приложение работает без чата.

Если группа понадобится снова: добавить бота в группу и перезапустить контейнер
— при старте он снова её проверит.

### 3.1 Идея «группа = команда» (не реализовано)

Задел под это уже есть в схеме: `organizations.group_chat_id` (миграция
`0055_org_bot.py`) и реестр `services/org_bots.py`, который знает «чей бот и чей
чат». Чтобы группа стала ещё и способом вступить в команду, нужно:

1. связать `organizations.group_chat_id` с операцией «все участники чата —
   члены команды» (по `chat_member` апдейтам, их надо добавить в
   `allowed_updates` вебхука);
2. решить конфликт ролей: пришедший из группы получает `staff`, а не `manager`;
3. не удалять из команды тех, кто вышел из чата, — иначе увольнение через
   Telegram станет побочным эффектом выхода из группы.

До этого решения группа остаётся только каналом анонсов.

## 4. Связка «Telegram + аккаунт приложения» (план)

Сейчас это два разных пользователя в `users`: `telegram_id=…` **или**
`email=…`. Слияние нужно, чтобы человек, пришедший из бота, мог потом войти по
почте (и наоборот), не теряя историю задач.

Что нужно сделать, по шагам:

1. **Схема.** Добавить `user_identities` (`user_id`, `kind`, `value`,
   `verified_at`) вместо двух nullable-колонок. Старые данные перенести
   миграцией: `telegram_id` → `('telegram', …)`, `email` → `('email', …)`.
   Уникальность — по `(kind, value)`.
2. **Привязка из Telegram.** Пользователь в боте нажимает «Привязать почту» →
   сервер выдаёт одноразовый код (TTL 10 минут, хранится хэшем) → в приложении
   он вводит код и пароль. Привязка идёт **в сессии Telegram**, то есть сервер
   точно знает, к какому `user_id` её прикрепить.
3. **Привязка из веб-версии.** Обратный сценарий: в приложении «Привязать
   Telegram» → deep-link `https://t.me/<bot>?start=link_<код>` → бот в личке
   подтверждает код и привязывает `telegram_id` к текущему `user_id`.
4. **Слияние двух готовых аккаунтов.** Самый дорогой случай (две истории
   задач). Правило: сливаем в аккаунт, к которому привязывают, а конфликты
   (две разные роли, два профиля в разных организациях) **показываем списком
   и просим выбрать**, а не решаем молча.
5. **Инварианты, которые нельзя терять:**
   * один Telegram-id не может быть привязан к двум `users`;
   * смена почты требует повторного подтверждения;
   * после слияния все сессии старого аккаунта гасятся;
   * `password_not_set` (у TG-пользователя нет пароля) должен предлагать
     «задать пароль», а не «неверный пароль».

До реализации этого плана в приложении уже работает всё, кроме слияния: вход по
почте, подтверждение адреса, сброс пароля, приглашения и роли.

## 5. Открытые вопросы

1. **`VAPID_PRIVATE_KEY` лежит на Amvera как обычная переменная** (не секрет) —
   её видно в панели без раскрытия. Пересоздать её как секрет стоит один
   перезапуск; сделать это лучше вне рабочего дня.
2. **Приглашения без Telegram** — маршрут работает, но в интерфейсе не хватает
   подсказки «ссылка для человека без Telegram»: сейчас приглашение
   подразумевает `t.me`.
3. **Уволенный из организации** остаётся пользователем: это правильно, но в
   интерфейсе нет способа увидеть «висящие» аккаунты без организации.
