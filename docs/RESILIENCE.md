# Отказоустойчивость: работа без VPN и локальный контур

Документ отвечает на два вопроса владельца:

1. как приложение работает **без VPN** в текущих российских условиях;
2. что можно сделать, чтобы **без интернета** оставался рабочий контур в
   пределах локальной сети.

Разделено на «уже сделано» (эта партия) и «предложения» с оценкой стоимости и
рисков. Ничего из раздела «предложения» не требует переписывания ядра: HR-логика
уже отделена от Telegram (`app/services/hr_*`), а фронт общается с API через один
`client.ts`.

## 1. Работа без VPN

Telegram в России работает; проблемы возникают у **инфраструктуры вокруг**:
Cloudflare, `api.telegram.org` в часы пик, Google. Поэтому схема — «RU-вход,
иностранное ядро, всё важное закешировано».

### 1.1. Свой домен и RU-прокси (P0, 1–2 дня)

```
Сотрудник → app.вашдомен.ru (RU VPS/облако, TLS, кэш статики)
                        ├── /api/*  → HF Space (FastAPI)  [прокси, keep-alive]
                        └── /      → собранный frontend
```

- Домен в зоне `.ru`, DNS у российского регистратора; Cloudflare как DNS/прокси
  не использовать — его в РФ периодически замедляют.
- TLS — Let's Encrypt на RU-хосте; приложение открывается по HTTPS, значит
  остаётся валидным Mini App URL.
- Статику (Vite-сборка) раздаёт RU-хост: если HF недоступен, интерфейс всё равно
  открывается и показывает понятную ошибку, а не белый экран.
- `VITE_API_BASE=https://app.вашдомен.ru` — фронт ходит только на свой домен.
  Резервный адрес вводится в профиле (см. таблицу выше).

Почему так, а не «жить на HF»: HF Space блокируется чаще и не даёт выбрать
российский IP; RU-прокси стоит ~300–600 ₽/мес и решает 80% проблем доступности.

### 1.2. Резервный контур (P0, полдня)

- Второй HF Space (или VPS) с тем же кодом и той же БД (Neon допускает несколько
  подключений), поднятый заранее.
- Проверка `/api/meta` (там `alembic_head` и fingerprint) раз в 5 минут с
  российского хоста; алерт админам в Telegram/на почту — до того, как начнут
  звонить сотрудники.
- Переключение — тем же полем «Сервер» в профиле. Это не автоматический failover
  (он дороже и опаснее), а управляемый: админ знает адрес резерва.

### 1.3. Bot API и вебхук (P1)

- Если `api.telegram.org` режет — `BOT_API_SERVER` уже поддерживается: свой
  прокси на Cloudflare Worker **или** на RU VPS (nginx `proxy_pass`).
- Вебхук Telegram должен смотреть на домен, который Telegram может доставить.
  Держите два URL (основной и резервный) и переключайте `setWebhook` скриптом
  `tools/` при аварии.
- Полный отказ Telegram: бот перестаёт слать напоминания, но приложение
  продолжает работать — уведомления копятся в «Центре уведомлений».

### 1.4. Google (P0, уже сделано)

Сервер забирает CSV и хранит снимок. Сотруднику Google не нужен вообще.
Если Google недоступен и серверу — показывается последняя рабочая версия с
пометкой «устарело» и кнопкой «Открыть таблицу» для тех, у кого доступ есть.

### 1.5. Мелочи, которые реально помогают

- Не грузить внешние шрифты/CDN: сейчас всё локальное — сохранить это правило.
- Service worker с кэшем оболочки (P2): приложение открывается офлайн и
  показывает последние данные (см. 2.3).
- Логи и метрики — на российском хосте, чтобы диагностика не зависела от
  заблокированного сервиса.

## 2. Локальная сеть без интернета

Ограничение честно: **Telegram Mini App без интернета не запускается** — он живёт
внутри Telegram и авторизуется подписью `initData`. Поэтому «локальный контур» —
это отдельный режим того же приложения, открываемый в браузере по адресу
локального сервера.

### 2.1. Целевая схема (P1, 3–5 дней)

```
Wi-Fi заведения
   ├── мини-ПК / NAS (Docker): postgres + backend(FastAPI) + caddy(TLS) + frontend
   ├── планшет/телефон сотрудника → https://shift.local
   └── (опционально) принтер чеков/кухни
```

- `docker compose` с четырьмя сервисами; данные — в локальном Postgres, фото —
  в `media_blobs` (уже так), материалы — из снимка (уже так).
- TLS: Caddy с внутренним CA; на планшетах один раз ставится корневой сертификат
  (или вход по HTTP в доверенной сети — хуже, но допустимо как временная мера).
- Часы/таймзона — из контейнера, NTP локального роутера.

### 2.2. Что нужно доделать в коде (единственное серьёзное изменение)

1. **Абстракция входа.** Сейчас `deps.py` проверяет только Telegram `initData`.
   Нужен второй провайдер: `local` — сотрудник выбирает себя из списка и вводит
   PIN (хэш в `employees.local_pin_hash`), сессия в HttpOnly-cookie. Включается
   переменной `AUTH_PROVIDERS=telegram,local`.
2. **Планировщик без Telegram.** `run_hr_tick` уже отделён от бота: напоминания
   пишутся в БД, доставка в Telegram — отдельный шаг. В локальном режиме шаг
   доставки отключается, уведомления видны в приложении.
3. **Экспорт/импорт для синхронизации.** Когда интернет вернулся: `pg_dump`
   локального контура + импорт в облако (или наоборот) с upsert по `id` и
   проверкой `updated_at`. Конфликты решать «кто позже», а не мержем полей.
4. **Резервные копии.** Ночной `pg_dump` на USB/NAS, ротация 14 дней, раз в
   месяц — проверка восстановления на чистой базе.

### 2.3. Более дешёвый промежуточный вариант (P0, полдня)

PWA-оболочка: service worker кэширует HTML/JS/CSS и последние ответы API
(чек-лист, задачи, табель, материалы). Без сети приложение открывается, данные
показываются «как есть», действия складываются в очередь и уходят при
восстановлении связи. Это **не** замена локальному серверу: общий чек-лист и
записи в БД без сети не появятся, но сотрудник не остаётся с белым экраном.

## 4. Риски и что не делать

- **Не** делать автоматический failover между базами: две БД без синхронизации
  дают «исчезнувшие» поручения, это хуже простоя.
- **Не** дублировать секреты в фронтенд: фото и материалы отдаёт сервер — не
  переносите подписанные ссылки в публичные плейлисты/чаты.
- **Не** держать единственную копию данных на HF Space: диск эфемерный, всё
  важное уже в Postgres.
- Локальный режим с PIN — компромисс по безопасности: включать только в
  доверенной сети, PIN минимум 6 цифр, блокировка после 5 попыток, журнал входов.

## 5. Как проверять обновление зависимостей (вывод аварии 26.10.2026)

Правило, которое стоило сломанного стенда: **прогон тестов не доказывает, что
зависимости ставятся**. Тесты бегут на том, что уже лежит в окружении, поэтому
несовместимость версий в них не видна — а на чистой сборке она валит контейнер.

Проверять так (по возрастанию силы доказательства):

1. `pip install --dry-run .` в пустом окружении — резолвер видит конфликт
   версий («ResolutionImpossible») до того, как он доедет до боевой сборки.
2. Собрать образ `docker build` локально там, где есть Docker.
3. Смотреть лог сборки хоста (`tools/hf-logs.py`, Amvera → `logs`) — стадия
   `BUILD_ERROR` вместе с `Runtime Error` в логе.

Отдельно: поднимая транзитивную зависимость (у нас так было с `aiohttp`),
смотреть, каким диапазоном её ограничивает тот, кто её притащил (`aiogram`
требовал `aiohttp<3.11`) — иначе поднятая версия не устанавливается вообще.
