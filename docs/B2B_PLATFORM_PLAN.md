# План: из приложения ресторана в B2B-пакет

Статус: **в работе** (начат 22.10.2026). Документ живой: у каждой фазы есть
критерий приёмки, а в конце — журнал прогресса. Пока критерий не выполнен,
галочка не ставится.

## Что продаём

Не «приложение для ресторана», а **ядро + отраслевой пакет + коннекторы**:

- **Ядро** — люди, роли, смены, задачи, чек-листы, обучение, KPI, лента,
  поручения, отчёты. Оно уже есть и от отрасли не зависит.
- **Отраслевой пакет** — данные, а не код: словарь терминов («зал» → «кабинет»,
  «смена» → «запись»), стартовые чек-листы, наборы KPI, категории проблем,
  шаблоны ролей. Один и тот же бинарь обслуживает салон, автосервис и магазин.
- **Коннекторы** — Yclients/iiko/1С/Google Sheets, публичный API и вебхуки.
  Тут же живут интеграции, которые «ждут контракта».

Правило, которое нельзя нарушать: **новый клиент — это строка в базе, а не
форк репозитория и не отдельный деплой**. Всё остальное в плане следует из него.

## Фаза 1. Мультитенантность (фундамент)

Без этого остальное не имеет смысла: сегодня в коде нет понятия «организация»,
есть один `BOT_TOKEN`, один `GROUP_CHAT_ID` и один набор настроек.

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 1.1 | `organizations`, `organization_members`, `org_id` у ключевых таблиц | миграция накатывается на тестовую PG и на прод без простоя |
| 1.2 | Тенант в зависимостях: `current_org` из членства пользователя | ручка без членства получает 403, а не данные первой организации |
| 1.3 | Скоуп всех запросов по `org_id` | тест «два тенанта не видят друг друга» на каждый ресурс |
| 1.4 | Уникальность внутри тенанта | `departments.slug`, `users.telegram_id`-подобные ключи уникальны в паре с `org_id` |
| 1.5 | Страж схемы | новая таблица без `org_id` роняет тест (ratchet: список легаси-таблиц только сокращается) |
| 1.6 | Бот на организацию | чат и токен привязаны к `org_id`; вебхук резолвит организацию по боту — **сделано** |

Фаза 1 закрыта целиком (22.10.2026). `org_id` есть у всех 72 бизнес-таблиц,
уникальные ключи переехали внутрь тенанта, фильтр запросов включён на уровне
сессии, страж схемы не оставляет лазеек. У организации может быть свой бот:
токен, секрет вебхука и чат лежат в `organizations`, входящий апдейт находит
организацию по секрету, `initData` проверяется токеном того бота, через
которого открыли мини-апп. Пустые поля означают «как раньше» — env-бот
обслуживает организацию по умолчанию, поэтому текущий контур не изменился.

Что осталось внутри фазы (долги, не блокирующие второго клиента):
`admin_config` пока общий (ключ станет составным `(org_id, key)`), планировщик
обходит только организацию по умолчанию — при втором клиенте его нужно
запускать по организациям, и единицы сырого SQL вне фильтра.

## Фаза 2. Вход и самостоятельность

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 2.1 | Почта/телефон как основной вход, Telegram — один из провайдеров | вход, выход, сброс, отзыв сессий без Telegram |
| 2.2 | Приглашения сотрудников ссылкой с ролью и сроком | приглашённый попадает в нужную организацию, а не в первую |
| 2.3 | PWA: манифест, иконки, установка, офлайн-оболочка | приложение ставится на домашний экран и открывается вне Telegram |
| 2.4 | Push вне Telegram (web push) + e-mail для важного | напоминание о смене доходит без Telegram |
| 2.5 | i18n (ru/en) | язык переключается без перезагрузки, тексты вне кода |

Состояние фазы 2 (23.10.2026): **2.1 закрыт** — на бэкенде аккаунт по почте,
пароль (PBKDF2), сессии с отзывом, сброс пароля по одноразовой ссылке, вход
`Authorization: Bearer`, членство в организации как условие доступа к данным.
Письма уходят через Resend (HTTP) или любой SMTP; без настроенного транспорта
режим «лог» — вход работает, письмо не отправляется, ссылка в журнал не
попадает. На фронте: экран входа/регистрации/сброса (`features/auth`), страница
`/reset?token=…` по ссылке из письма, `401` без `initData` открывает форму,
`403 org_required` — экран «ждём приглашения», `org_inactive` — «организация на
паузе». Шаг 2.2 тоже закрыт: ссылка-приглашение с ролью и сроком, страница
`/invite?token=…`, раздел «Приглашения» в админке. Шаг 2.3 закрыт: манифест,
иконки, service worker с офлайн-оболочкой и подсказка об установке на домашний
экран. Шаг 2.4 закрыт: подписка браузера (`push_subscriptions`), отправка
напоминаний о сроке через web push, письмо как запасной канал для важного и
тестовая кнопка в профиле. Подтверждение адреса почты тоже сделано: ссылка
`/verify?token=…` живёт двое суток, письмо уходит при регистрации и по кнопке
в профиле, повторный клик считается успехом. Шаг 2.5 (i18n) сделан на уровне
основы: язык переключается без перезагрузки, тексты входа, приглашения, сброса,
подтверждения почты, навигации и шапки профиля лежат в словаре `src/i18n`, а не
в разметке. Экраны внутри приложения (лента, задачи, табели, админка) пока
русские: их тексты переезжают по одному, инфраструктура для этого готова.

Почему не перевели всё сразу. В интерфейсе ~1900 строк с кириллицей в 112
файлах. Один заход «перевести всё» даёт либо машинный английский, либо
полурусские экраны с английскими кнопками — хуже, чем сегодняшняя цельность.
Поэтому шаг 2.5 закрыт как **механизм**: словарь с проверкой полноты на этапе
сборки, переключатель, перевод кодов ошибок сервера, `html lang`, сохранение
выбора. Дальше каждый экран переводится отдельной правкой и проверяется тестом.

Почему без нового SDK: писем два типа (сброс и приглашение), а провайдера
выбирает клиент — российский SMTP или зарубежный HTTP. Тонкий слой
`services/mail.py` позволяет сменить провайдера настройками, а не кодом.

### Тарифы, лимиты и триал (фаза 4, шаг 4.1, 02.11.2026)

До этого шага организация могла расти без границ: сто человек и сорок отделов
работали одинаково с одним мастером и одной сменой. Продавать такое можно
только на доверии, а обещание «до 15 сотрудников» проверить было нечем — в
коде не существовало ни одного места, где звучало бы «нельзя».

Правило шага: **граница — это отказ с причиной, а не пятисотая и не тишина.**

- [x] Каталог тарифов в одном месте (`services/billing.py`): пробный (10 мест,
      5 подразделений), «Начало» (15), «Бизнес» (50), «Сеть» (200). Код, а не
      таблица: тарифы меняются вместе с продуктом и ревьюятся в диффе; таблица
      появится на шаге 4.3, когда их будет править платформа.
- [x] Новая организация создаётся сразу на триале с датой окончания (14 дней),
      а существующие получают «Бизнес» без срока. Иначе введение тарифов
      выглядело бы как поломка у действующего клиента.
- [x] Место занимает живой человек **и** непринятое приглашение: ссылка уже
      обещает место, и двадцать ссылок при лимите десять — обход лимита, а не
      забота о людях. Демо-профили `[BOT]` и теневые профили проверки не
      считаются.
- [x] Отказы с кодами: `seats_limit` и `branches_limit` — 409, `trial_expired`
      — 402. Проверка стоит там, где происходит рост: создание приглашения,
      ручное создание подразделения и мастер настройки (пакетом, чтобы отказ
      на третьем отделе из пяти не оставлял мастер наполовину применённым).
- [x] Экран «Тариф и лимиты» в кабинете: тариф, остаток триала, две полосы
      «занято из лимита» и честный текст, что по окончании триала работа
      продолжается, а закрыт только рост.
- [ ] Осталось: цены и оплата (шаг 4.2), «филиалы» как отдельные организации
      сети — сейчас лимит считается по подразделениям одной организации.

### Счета и продление подписки (фаза 4, шаг 4.2, 03.11.2026)

На шаге 4.1 у тарифа были лимиты, но не было цены: экран честно говорил
«напишите нам». Это работает для первых десяти клиентов и перестаёт работать
на одиннадцатом — половина людей не пишет письмо «а сколько стоит».

Главная развилка шага: подключать ЮKassa/CloudPayments или сначала счёт.
Провайдер требует ключей мерчанта и юридических данных, которых у нас нет, а
кнопка «Оплатить», которая ничего не делает, хуже её отсутствия. Поэтому
сделаны счета — документ, который существует независимо от провайдера: номер,
тариф, период, сумма, срок. Когда провайдер появится, он будет закрывать те же
счета, и история платежей не переедет.

- [x] Цены в каталоге (`services/billing.py`): «Начало» 2 900 ₽/мес,
      «Бизнес» 7 900 ₽/мес, «Сеть» 19 900 ₽/мес; год — десять месяцев.
      Цифры лежат одной таблицей, чтобы правка была в одном месте и в диффе.
      **Это предложение владельцу, а не согласованный прайс.**
- [x] Таблица `org_invoices` (миграция `0066`) и `organizations.plan_ends_at`.
      Сумма берётся из каталога, а не из тела запроса: клиент не выбирает,
      сколько платить. Периоды в днях (30 и 365), а не в «месяцах» — иначе
      годовой тариф тихо укорачивался бы на пять дней.
- [x] Повторный клик «выставить счёт» возвращает уже открытый счёт на тот же
      тариф и период: два одинаковых документа в бухгалтерии клиента выглядят
      как двойное списание, даже когда денег никто не брал.
- [x] Владелец может только *попросить* подтвердить оплату: кнопка «Я оплатил»
      переводит счёт в ожидание. Продлевает подписку `billing.mark_paid` —
      вызывается платформой (админка на шаге 4.3) или провайдером. Кнопка,
      которая продлевает тариф сама, была бы бесплатным безлимитом.
- [x] Продление складывается: второй платёж добавляет период к уже оплаченному
      сроку, а не затирает его. Оплаченный тариф снимает триал.
- [x] Просроченная оплата закрывает рост (`subscription_expired`, 402), но не
      работу: люди и данные на месте. У старых организаций срока нет вообще —
      «бессрочно» это не «истекло вчера».
- [x] Просроченный счёт не хранится статусом: `expired` считается из срока, и
      фоновой задачи, которая переводит строки, не нужно.
- [x] Экран «Оплата и счета» в кабинете: тариф, срок оплаты, витрина с ценами
      за месяц и год, список счетов со статусами и действиями.
- [ ] Осталось: платёжный провайдер и автоматическое закрытие счетов по
      вебхуку, чеки (54-ФЗ), автопродление с карты. Всё это требует ключей
      владельца, поэтому в код пока не входит.

### Админка платформы (фаза 4, шаг 4.3, 03.11.2026)

До этого шага всё, что не влезало в кабинет клиента, делалось руками в базе:
продлить тариф, заблокировать неоплатившего, подтвердить оплату. Поддержка не
должна ходить в SQL — одна опечатка в `org_id` меняет чужую организацию.

Главное решение: **два разных «админа» — это две разные роли.** Роль `admin`
внутри организации выдаётся владельцу салона и снимается там же; доступ к
платформе — это Telegram-id из `ADMIN_TG_IDS`/встроенной пары. Смешать их
значило бы отдать владельцу салона список конкурентов.

- [x] Роутер `/api/platform/*` отдельно от `/api/org/*`: список организаций,
      сводка, смена тарифа, блокировка, счета всех клиентов.
- [x] Обход тенантов через `all_orgs()` — единственное законное место такого
      обхода: без него платформа видела бы только организацию из фильтра (то
      есть первую) и список всегда был бы из одной строки.
- [x] Подтверждение оплаты (`mark_paid`) живёт здесь. Клиентская кнопка «я
      оплатил» только просит подтверждения; продлевает подписку платформа.
      Это закрывает цикл шага 4.2: счёт → оплата → продление.
- [x] Блокировка (`is_active=false`) закрывает вход сразу: `current_org` отдаёт
      403 на следующем запросе, а не после истечения сессии.
- [x] Поиск по имени и коду + пагинация: поддержка ищет «Салон на Ленина» или
      `salon-lenina`, а не помнит id.
- [x] Каталог тарифов (коды и цены) приходит с сервера в сводке. Константа на
      фронте означала бы, что новый тариф есть на сервере, но назначить его
      нельзя.
- [x] Экран «Платформа» в системной группе кабинета: виден только владельцу
      продукта (`platform`), клиенту — нет. Сводка, клиенты с выбором тарифа и
      блокировкой, счета с подтверждением.
- [ ] Осталось: перенос данных между организациями (удаление организации
      и журнал действий закрыты шагом 5.5)
      платформы, ручное продление без счёта (сейчас — только через счёт).

Проверка: бэкенд 1802 passed, 11 skipped (5 новых тестов: клиентский админ не
получает доступ, список видит оба тенанта, смена тарифа снимает триал и
блокировка сохраняется, подтверждение счёта продлевает подписку, сводка считает
триал и деньги); фронт 751 passed (86 файла, 4 новых теста экрана),

### Свой бренд вместо SemiTaskBot (фаза 4, шаг 4.4, 03.11.2026)

Продукт назывался SemiTaskBot у всех клиентов: салон показывал команде чужое
имя, а логотип и цвет были платформенными. Это последнее, что мешало продать
приложение как «своё», — клиент открывал его и видел чужой бренд.

- [x] Поля `brand_name`, `brand_color`, `brand_logo_url` (миграция `0067`).
      Пусто — «бренд не настроен»: клиент видит имя организации, а не имя
      платформы и не пустой заголовок.
- [x] Цвет нормализуется (`#ABC` → `#aabbcc`). Иначе одно и то же значение
      копилось бы в разных написаниях, а сравнение «изменился ли бренд» врало.
- [x] Логотип — только `https`-ссылка. `javascript:`/`data:` — не картинка, а
      дыра; `http` браузер на телефоне блокирует как смешанный контент.
      Загрузка файла не сделана намеренно: она требует хранилища и чистки
      сирот, а поле при её появлении останется тем же.
- [x] Имя не сбрасывается пустым значением: пустое имя — забытое поле, а не
      «бренд без имени». Полный сброс — отдельная ручка, она возвращает имя
      организации.

### CI на каждый пуш (фаза 5, шаг 5.1, 03.11.2026)

До этого шага «всё зелёное» означало «зелёное на моей машине»: локальная
`.venv` с нужными пакетами, локальный `node_modules`, забытый экспорт
переменных. Пуш в `main` мог привезти красные тесты, и узнавали об этом на
следующем деплое или от клиента.

- [x] `.github/workflows/ci.yml`: два джоба на каждый пуш в `main` и на каждый
      pull request. Backend — `pip install -e ".[dev]"` и полный `pytest`;
      frontend — `npm ci`, `npm run typecheck`, `vitest run`, `npm run build`.
- [x] Те же команды, что запускаются руками. Любая «особая» команда в CI через
      месяц расходится с рабочей машиной, и зелёный CI перестаёт что-либо
      значить. Исключений два: `maxForks=2` у vitest (без него прогон падает по
      таймаутам на 2 vCPU) и `npm ci` вместо `npm install` (lock-файл — источник
      правды).
- [x] Переменные окружения заданы явно: тесты выставляют их сами, но прогон не
      должен зависеть от того, что каждый файл не забыл это сделать.
- [x] Линтер намеренно не включён: в проекте нет `eslint.config.*`, и шаг падал
      бы на конфиге, а не на коде. Красный CI из-за отсутствующего конфига учит
      игнорировать красный — это хуже, чем не иметь проверки.
- [x] `docs/CI.md`: что проверяется, как посмотреть прогон и как включить
      «Require status checks to pass» (с `gh api` и через веб-интерфейс).
- [ ] Осталось: включить блокировку мёржа в настройках репозитория. Это правило
      GitHub, для него нужны права администратора репозитория — у агента нет
      токена с такими правами, поэтому шаг за владельцем (инструкция готова).

Проверка: локально прогнаны те же команды, что в CI — бэкенд 1813 passed,
11 skipped; фронт 759 passed (87 файла), `tsc` чисто, сборка успешна.
Новых тестов нет: шаг про инфраструктуру, и его собственный результат — прогон
CI на чистой машине.

Первый прогон CI был красным и нашёл настоящую проблему: пять тестов CORS
проходили локально только потому, что `CORS_ORIGINS` лежал в `.env`
разработчика, а на чистой машине список пуст. Тесты теперь сами задают
окружение и чистят кеш настроек. Прогон на коммите `7add435` — зелёный

### Лимиты и квоты организации (фаза 5, шаг 5.3, 03.11.2026)

Лимит частоты считался по адресу посетителя. Для публичных ручек это
правильно, для рабочих — нет: за одним офисным NAT сидит вся смена, и
клиент с сотней людей получал тот же потолок, что и клиент с пятью. И
наоборот: один клиент, разогнавший скрипт, занимал общий API — ровно то,
что шаг обязан исключить.

- [x] `backend/app/services/org_limits.py`: частота считается **по
      организации**, ключ — `org_id`, а не IP (перебор адресов лимит не
      снимает и не наказывает соседей по офису). Потолок задаёт тариф:
      `Plan.api_rpm` — 300 / 600 / 1200 / 2400 запросов в минуту.
- [x] Проверка стоит в зависимостях (`deps.current_user`,
      `deps.current_employee`), а не в middleware: организация известна
      только после аутентификации, и второй раз разбирать подпись
      `initData`/сессию ради счётчика не нужно.
- [x] Один запрос — одно списание: флаг `begin_request()` ставится в
      начале запроса, иначе пользователь и сотрудник в одном запросе
      списывали бы две единицы, а фактический лимит был бы вдвое ниже
      обещанного.
- [x] `429` с `Retry-After` и `X-RateLimit-Limit` /
      `X-RateLimit-Remaining` / `X-RateLimit-Reset`: клиент видит границу
      тарифа, а не «что-то пошло не так».
- [x] Квота медиа по тарифу (`Plan.storage_mb` — 200 МБ … 20 ГБ)
      проверяется ДО вставки блоба: отказ после `INSERT` всё равно
      оставил бы запись и счётчик. Превышение — `413 storage_full`, это
      не битый файл, а граница квоты.
- [x] Тариф кэшируется на минуту и сбрасывается при оплате счёта
      (`billing.mark_paid`): иначе клиент после оплаты минуту жил бы со
      старым потолком и получал `429`, за который уже заплатил.
- [x] При недоступной базе работает минимальный потолок (`FALLBACK_RPM`),
      а не отказ: лимит защищает от перегрузки и не должен сам ею стать.
- [x] `docs/QUOTAS.md`: цифры, механизм, чего сознательно нет, как
      разбирать `429`/`413` у клиента.
- [ ] Осталось: общий счётчик между репликами (Redis или таблица) —
      вместе с горизонтальным масштабированием; квота на «тяжёлые»
      операции, когда такие появятся.

Проверка: 11 новых тестов — тарифные потолки, изоляция организаций,
`429` с заголовками, одно списание на запрос, выключатель для
нагрузочных проб, пропуск без организации, кэш и сброс тарифа,

### Бэкапы и проверка восстановления (фаза 5, шаг 5.4, 04.11.2026)

Проверка шага началась с вопроса «а что у нас есть» — и ответа не было:
единственный дамп снят **29.09.2026** на миграции `0022` (33 таблицы, 531

То есть «бэкап» снялся бы с сервера, на который никто не откатывается:
файлы на месте, хэши сходятся, данных боевой базы в нём нет. Плюс сами
инструменты жили вне git — CI их не видел, на другой машине их бы не было.

Критерий шага — «восстановление проверено, а не обещано», поэтому сделано
не расписание, а доказательство:

- [x] `tools/backup-db.py` и `tools/db-rehearsal.py` перенесены в репозиторий
      (вне git их не мог запускать ни CI, ни новая машина).
- [x] `dump` сверяет хост DSN с боевой базой из `/api/meta` и отказывается
      снимать копию «не той базы»; копия стенда — только явным `--allow-any`.
      Сравнение по префиксу: боевой DSN идёт через `-pooler`, а `/api/meta`
      маскирует хвост (`ep-dry-cherry-….neon.tech`).
- [x] `verify` считает пустой дамп ошибкой: целые файлы без строк — не точка
      отката.
- [x] `prune --keep N` — ротация: без неё дампы занимают диск до отказа, а
      отказ диска — это отказ записи.
- [x] `db-rehearsal.py rehearse-local` восстанавливает дамп в **одноразовый**
      Postgres в Docker и сверяет построчно. Боевая инфраструктура не
      участвует: проверка не требует прав на прод и не оставляет мусор при
      прерванном прогоне.
- [x] `db-rehearsal.py check DIR --dsn …` — сверка уже восстановленной базы
      (для CI, где Postgres поднимает сам workflow).
- [x] `.github/workflows/backup.yml`: ежедневно дамп + проверка + артефакт

- [x] `backups/` в `.gitignore`: дампы — данные клиентов.
- [x] Найден и исправлен баг миграций: `alembic/env.py` включал SSL

- [x] `docs/BACKUPS.md`: RPO/RTO, расписание, порядок восстановления,
      ограничения и что именно проверено.
- [ ] Осталось: секрет `DATABASE_URL` в GitHub Actions добавляет владелец

### Приватность: экспорт, удаление, сроки, аудит (фаза 5, шаг 5.5, 04.11.2026)

Критерий шага — «клиент получает свои данные и удаление по запросу» — до этого
не выполнялся ни в одной части: «дайте копию» и «удалите нас» означали письмо в
поддержку и ручную работу в базе. Для B2B это не последняя галочка: клиент
выбирает сервис в том числе по тому, может ли он уйти.

- [x] Выгрузка `GET /api/org/export` (только владелец): организация, участники,
      подразделения, сотрудники и сроки — файлом JSON. Токенов приглашений в
      файле нет: в базе только SHA-256, восстановить ссылку нельзя.
- [x] Удаление `DELETE /api/org` с подтверждением кодом организации, а не
      кнопкой «да»: удаление необратимо, и диалог подтверждения закрывают не

### Публичный API и вебхуки (фаза 6, шаг 6.1, 04.11.2026)

Критерий шага — «интегратор подключается без доступа к базе» — не выполнялся:
единственным способом отдать данные наружу был пароль владельца, а он открывает
всё, включая удаление организации.

**Ключ вместо пароля.** `api_keys` (миграция `0069`): организация, имя, префикс,
SHA-256 токена, набор прав, `last_used_at`, `revoked_at`. Ключ показывается один
раз; утечка дампа не даёт доступа. Права закрытые: `people.read`,
`schedule.read`, `menu.read`, `contacts.read` — почта не уезжает по умолчанию.
Неизвестное право — `400`, а не молча отброшенное: иначе интегратор получает
`403` на ручке, которую считал разрешённой, и разбор начинается с чужой стороны.

**Публичный API `/api/v1`** — только чтение: `me`, `departments`, `employees`,
`shifts?from&to`, `menu`. Организацию даёт строка ключа, а не заголовок, поэтому
подставить чужой id нечем. Контакты — только с `contacts.read`. Период графика
не больше 92 дней; пустая ячейка отсутствует в ответе, а не приходит `null`-днём.
Лимит частоты — по организации (тариф), а не по IP.

**Вебхуки.** `webhook_endpoints` и `webhook_deliveries`: события
`employee.created/updated/deactivated` ставятся в очередь в той же транзакции,
что и изменение, и уходят из ежедневного `run_hr_tick`. Подпись
`X-SemiTask-Signature` — HMAC-SHA256 от сырого тела. До 5 попыток (1 мин, 5 мин,
30 мин, 2 ч, 6 ч), тело повтора — снимок первой попытки; после пятой — `failed` в
журнале, приёмник не выключается сам. Журнал 30 дней. Только `https`, без
логина в URL и приватных адресов — защита от SSRF, остаточный риск с DNS назван
в коде и в `docs/API.md`.

**Кабинет.** Раздел «Интеграции» (группа «Настройки», только владелец): создать
ключ и увидеть его один раз, отозвать, добавить вебхук и увидеть секрет один раз,
включить/выключить, посмотреть последние доставки с кодами. Создание и отзыв
пишутся в журнал аудита (шаг 5.5).

Проверка: бэкенд **1857 passed, 11 skipped**, 12 новых тестов интеграций; фронт
**774 passed** (90 файлов), `tsc` чисто. После деплоя: сверка head с боевыми
базами — 3 passed, `/api/meta` `db = head = 0069_api_integrations`, `/readyz`
200, `/api/v1/me`, `/api/org/api-keys`, `/api/org/webhooks` и журнал доставок
без входа — 401; CI на `ceff812` — success; Pages `d15b87b1`. Живьём не проверено:
создание ключа и реальная доставка вебхука на внешний приёмник — нужен вход
владельца и чужой сервер; доставка проверена тестом с подменённым HTTP-клиентом.

уходили всем, у кого есть Telegram: одна и та же логика в трёх местах означала
бы, что новый вид тихо пролезет мимо правила.

**Что сделано.**

- [x] `notify_prefs.KINDS = ("digest", "deadline", "escalation")`. Список

### Входящий обмен по ключу API (фаза 6, шаг 6.2, часть, 04.11.2026)

Критерий шага — «обмен идёт по контракту, ошибки видны в журнале» — упирается в
два разных препятствия. Yclients и iiko требуют подписанного контракта с
вендором (внешняя блокировка), а 1С и Excel не требуют ничего: они умеют отдать
CSV по расписанию. Поэтому шаг закрыт с той стороны, где нет чужой подписи.

**Что сделано.**

- [x] `POST /api/v1/import/preview` — разбор без записи. Право на вид данных
      проверяется **до** ответа: `people.write` для людей, `schedule.write` для
      графика.
- [x] `POST /api/v1/import/apply` — применение того же разбора, что у экрана
      импорта (один код, а не второй путь создания людей).
- [x] `Idempotency-Key`. 1С повторяет запрос при таймауте; без ключа повтор
      создал бы второго человека, а с `overwrite` стёр бы актуальный график.
      Повтор с тем же ключом получает сохранённый ответ и не трогает данные;
      тот же ключ с другим файлом — 409, потому что это уже не повтор.
- [x] Права записи отдельно от чтения (`people.write`, `schedule.write`).
      Дефолт ключа остался read-only: выдать запись — осознанное действие
      владельца, и оно видно в списке ключей.
- [x] Журнал `api_import_runs` (миграция `0071`): числа
      создано/обновлено/пропущено/ошибок, имя файла, ключ идемпотентности,
      снимок ответа. Читается интегратором (`GET /api/v1/import/runs`) и
      владельцем в кабинете (`GET /api/org/import-runs`), плюс событие аудита
      `import.api`.
- [x] Кабинет: блок «Импорты по API» рядом с вебхуками и права записи в списке
      прав ключа. Без этого «ошибки видны в журнале» означало бы «видны, если
      залезть в базу».

**Чего сознательно нет.** Нет исходящих коннекторов и OAuth к Yclients/iiko:
это отдельный контракт, и придумывать его за вендора — гарантированная
переделка. Нет маппинга полей iiko: формат обмена совпадает с CSV-импортом,
иначе пришлось бы поддерживать два разбора одной таблицы.

Проверка: 7 новых тестов (`test_api_ingest.py`: отказ без права до записи,
применение и журнал, повтор по ключу, конфликт ключа с другим файлом, смены
только с `schedule.write`, порядок журнала, монтирование путей), инварианты
схемы и публичных маршрутов обновлены осознанно; бэкенд 1881 passed, 11 skipped
(кроме теста головы боевой базы — он закрывается деплоем), фронт 789 passed,

## Риски

1. **Полу-мультитенантность хуже её отсутствия.** Пока не все запросы скоупятся,
   второй клиент заводить нельзя: данные протекут. Поэтому фаза 1 идёт первой и
   целиком, а не «по частям в прод».
2. **Форк на клиента.** Любое «сделаем ветку для салона» убивает пакет. Только
   данные, пакеты и настройки.
3. **Default-org как костыль.** Пока у таблиц `server_default=1`, новая строка
   без явного `org_id` молча уедет в первую организацию. Страж и тесты должны
   успеть раньше, чем появится второй клиент.
4. **Telegram как единственный канал.** Для части B2B это стоп-фактор, отсюда
   фаза 2.
