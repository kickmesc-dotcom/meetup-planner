# План: из приложения ресторана в B2B-пакет

Статус: **в работе** (начат 22.10.2026). Документ живой: у каждой фазы есть
критерий приёмки, а в конце — журнал прогресса. Пока критерий не выполнен,
галочка не ставится.

## Что продаём

Не «приложение для ресторана», а **ядро + отраслевой пакет + коннекторы**:

- **Ядро** — люди, роли, смены, задачи, чек-листы, обучение, KPI, лента,
  поручения, отчёты. Оно уже есть и от отрасли не зависит.
- **Отраслевой пакет** — данные, а не код: словарь терминов («зал» → «кабинет»,
  «смена» → «запись»), стартовые чек-листы, наборы KPI, категории проблем,
  шаблоны ролей. Один и тот же бинарь обслуживает салон, автосервис и магазин.
- **Коннекторы** — Yclients/iiko/1С/Google Sheets, публичный API и вебхуки.
  Тут же живут интеграции, которые «ждут контракта».

Правило, которое нельзя нарушать: **новый клиент — это строка в базе, а не
форк репозитория и не отдельный деплой**. Всё остальное в плане следует из него.

## Фаза 1. Мультитенантность (фундамент)

Без этого остальное не имеет смысла: сегодня в коде нет понятия «организация»,
есть один `BOT_TOKEN`, один `GROUP_CHAT_ID` и один набор настроек.

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 1.1 | `organizations`, `organization_members`, `org_id` у ключевых таблиц | миграция накатывается на тестовую PG и на прод без простоя |
| 1.2 | Тенант в зависимостях: `current_org` из членства пользователя | ручка без членства получает 403, а не данные первой организации |
| 1.3 | Скоуп всех запросов по `org_id` | тест «два тенанта не видят друг друга» на каждый ресурс |
| 1.4 | Уникальность внутри тенанта | `departments.slug`, `users.telegram_id`-подобные ключи уникальны в паре с `org_id` |
| 1.5 | Страж схемы | новая таблица без `org_id` роняет тест (ratchet: список легаси-таблиц только сокращается) |
| 1.6 | Бот на организацию | чат и токен привязаны к `org_id`; вебхук резолвит организацию по боту |

Сейчас (22.10.2026) сделаны 1.1 частично (`employees`, `departments`),
1.5 и заготовка 1.2. Остальные 60+ таблиц ждут своей миграции — страж печатает
их списком.

## Фаза 2. Вход и самостоятельность

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 2.1 | Почта/телефон как основной вход, Telegram — один из провайдеров | вход, выход, сброс, отзыв сессий без Telegram |
| 2.2 | Приглашения сотрудников ссылкой с ролью и сроком | приглашённый попадает в нужную организацию, а не в первую |
| 2.3 | PWA: манифест, иконки, установка, офлайн-оболочка | приложение ставится на домашний экран и открывается вне Telegram |
| 2.4 | Push вне Telegram (web push) + e-mail для важного | напоминание о смене доходит без Telegram |
| 2.5 | i18n (ru/en) | язык переключается без перезагрузки, тексты вне кода |

## Фаза 3. Отраслевые пакеты

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 3.1 | Словарь терминов организации поверх `app.texts` | «Залы» → «Кабинеты» без правки кода |
| 3.2 | Три стартовых пакета: салон, автосервис, розница | новая организация получает чек-листы, KPI и роли из пакета |
| 3.3 | Демо-данные пакета (уже есть `hr_demo`) | витрина «покажем на ваших данных за 5 минут» |
| 3.4 | Мастер онбординга: отрасль → люди → график → первый чек-лист | новая организация проходит путь без разработчика |

## Фаза 4. Деньги и границы

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 4.1 | Тарифы, лимиты (сотрудники, филиалы), триал | при превышении лимита понятный отказ, а не 500 |
| 4.2 | Оплата (ЮKassa/CloudPayments) и счета | подписка продлевается, чек приходит |

| 4.4 | White-label: логотип, цвета, домен, имя бота | клиент видит свой бренд, а не SemiTaskBot |

## Фаза 5. Эксплуатация и доверие

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 5.1 | CI: pytest, vitest, tsc, сборка на каждый пуш | красный CI блокирует мёрж |
| 5.2 | Мониторинг: ошибки, latency, алерты | падение видно до жалобы клиента |
| 5.3 | Rate limit и квоты по организации | один клиент не кладёт API остальным |
| 5.4 | Бэкапы с проверкой восстановления, PITR | восстановление проверено, а не обещано |
| 5.5 | Приватность: экспорт, удаление, сроки хранения, аудит доступа | клиент получает свои данные и удаление по запросу |

## Фаза 6. Коннекторы

| Шаг | Что именно | Критерий приёмки |
| --- | --- | --- |
| 6.1 | Публичный API + вебхуки с ключами по организации | интегратор подключается без доступа к базе |
| 6.2 | Yclients (салоны), iiko (общепит), 1С/Excel (учёт) | обмен идёт по контракту, ошибки видны в журнале |
| 6.3 | Импорт из Excel/CSV | люди и график заводятся за минуты |

Интеграции iiko и внешнего графика по-прежнему ждут подтверждённого контракта
(см. `MEGAPROMT3_PLAN.md`) — это внешняя блокировка, не наша.

## Риски

1. **Полу-мультитенантность хуже её отсутствия.** Пока не все запросы скоупятся,
   второй клиент заводить нельзя: данные протекут. Поэтому фаза 1 идёт первой и
   целиком, а не «по частям в прод».
2. **Форк на клиента.** Любое «сделаем ветку для салона» убивает пакет. Только
   данные, пакеты и настройки.
3. **Default-org как костыль.** Пока у таблиц `server_default=1`, новая строка
   без явного `org_id` молча уедет в первую организацию. Страж и тесты должны
   успеть раньше, чем появится второй клиент.
4. **Telegram как единственный канал.** Для части B2B это стоп-фактор, отсюда
   фаза 2.
