# Где держать приложение и базу: Amvera против Neon

Разбор 31.10.2026, после письма Neon о 80% квоты и ревизии проектов Amvera.
Цены — официальные страницы провайдеров на эту дату; курс доллара взят
**1 USD = 90 ₽** (допущение, а не факт — при другом курсе пересчитайте строки,
где есть $).

## 1. Что есть сейчас (факты, а не предположения)

**Amvera, регион Warsaw-0** (namespace `tenant-ru-youmakemefry`):

| Проект | Статус | Домен | Обслуживает приложение |
|---|---|---|---|
| `meetup-planner` | RUNNING, 1 инстанс | `meetup-planner-youmakemefry.waw0.amvera.tech` | **да** — сюда смотрит `PUBLIC_BASE_URL` и вебхук |
| `semitask` | RUNNING, 1 инстанс | `semitask-…` — **active=false** | нет |
| `semitaskbot` | RUNNING, 1 инстанс | `semitaskbot-…` — **active=false** | нет |

Два последних проекта работают, но трафика не получают: их домены
деактивированы, а приложение ходит только в `meetup-planner`. Это прямые
деньги за простаивающие контейнеры.

**Neon:** 15 МБ данных, 8 пользователей, крупнейшая таблица — 62 строки.
Израсходовано 80,1 из 100 CU-часов; при текущем темпе (≈2,6 CU-ч в сутки)
осталось около **8 суток** до отказа.

Вывод, который напрашивался: отдельная managed-база с квотой в CU-часах
обслуживает 15 МБ и восемь человек. Это не «масштаб», это накладные расходы.

## 2. Сколько это стоит в рублях

Тарифы Amvera: приложение «Начальный» — 290 ₽/мес (0,25 vCPU / 0,5 ГБ),
«Пробный» — 170 ₽/мес, «Начальный Плюс» — 490 ₽/мес. Managed PostgreSQL —
**290 ₽/мес** за реплику (0,5 ГБ ОЗУ, до 0,1 vCPU) плюс **18 ₽ за 1 ГБ** диска;
бэкапы глубиной 7 дней включены. Neon Launch — **$19/мес**, то есть ≈1 710 ₽
при курсе 90.

| Вариант | Что входит | ₽/мес |
|---|---|---|
| **Сегодня** | 3 приложения Amvera + Neon free | **870** (через ~8 суток Neon останавливает compute) |
| **Сегодня + Neon Launch** | то же, но база по подписке | **2 580** |
| **Только база на Amvera (рекомендую)** | 1 приложение (290) + PG «Начальный» (290) + 1 ГБ диска (18) | **598** |
| Тот же вариант, «Пробный» для приложения | 170 + 290 + 18 | **478** |
| Своя виртуалка | приложение + PostgreSQL + бэкапы на вашей VM | маржинально **0 ₽** (VM уже оплачена), но появляется ручная работа |

Разница между «сегодня + Neon Launch» и «одно приложение + PG на Amvera» —
около **1 980 ₽ в месяц**, причём в варианте с Amvera бэкапы глубже
(7 дней против 0,3 дня на бесплатном Neon), а второй панели для баз больше нет.

Про «две реплики» на скриншоте: у `meetup-planner` стоит инстанс 1, но
автомасштабирование может поднимать второй на пике. Это не второй проект, а
второй контейнер того же проекта — и на тарифе с лимитом 0,25 vCPU он упирается
в потолок (в интерфейсе «Потребление выше 85%»).

## 3. Сравнение по существу, а не по цене

| Критерий | Neon (как сейчас) | Managed PostgreSQL в Amvera | Своя VM |
|---|---|---|---|
| Цена при нашем объёме | $19/мес после квоты | 308 ₽/мес | 0 ₽ сверх VM |
| Латентность для Telegram-приложения | база в eu-central, API в Warsaw — запрос «через пол-Европы» | база рядом с API, один регион | зависит от VM |
| Управляемые бэкапы | 0,3 дня бесплатно, 7 дней — на платном | **7 дней включены**, ежедневно | делать самому (cron + выгрузка) |
| Точка отказа | две независимые инфраструктуры: API жив, база «уснула» | одна панель, один счёт | всё на вас: диск, ОС, обновления |
| Масштабирование | compute units, автопауза | реплики 1→5, тариф шагом | руками |
| Переезд региона | проект в другом регионе | Москва/СПб ↔ Варшава переключением | пересоздание VM |
| Прозрачность расходов | CU-часы, которые трудно предсказать | фиксированный ₽/мес за реплику | фиксированная аренда |
| Наши данные | 15 МБ | 15 МБ | 15 МБ |

**Почему не «русский канал».** Важно: наши проекты Amvera уже стоят в
**Warsaw-0**, а не в СПб. То есть переход на Amvera-PG не отправляет
Telegram-трафик через российскую инфраструктуру: API и база остаются в
Варшаве, ближе к европейским выходам Telegram. Это тот же довод, которым вы
сами возражали против РФ-канала, и он сохраняется.

**Почему VM пока не основной вариант.** Маржинальная цена нулевая, но вы
покупаете себе: ручные бэкапы (иначе 15 МБ исчезнут вместе с диском),
обновления ОС и PostgreSQL, TLS-сертификаты, мониторинг «контейнер жив, а база
нет», деплой без панели. На пилоте с сотрудниками это худший момент для
переезда на самообслуживание. VM разумно держать как резервный контур —
например, для старой версии бота (см. `LEGACY_BOT_RUNBOOK.md`), где нагрузка
нулевая и потеря не критична.

## 4. Рекомендация

1. **Заморозить `semitask` и `semitaskbot`** — они не обслуживают трафик.
   Заморозка обратима (проект не удаляется), экономия ≈580 ₽/мес.
2. **Перевести базу на Managed PostgreSQL в Amvera (Warsaw)**. Итог: одно
   приложение + одна база рядом, ≈598 ₽/мес, бэкапы 7 дней.
3. **Neon оставить на неделю** после переключения как точку отката, затем
   удалить проект, чтобы квота не капала.
4. **VM** — под старую версию/эксперименты, не под боевой контур пилота.

## 5. План переезда базы (15 МБ, без простоя)

Данные крошечные, поэтому перенос делается копией, а не «переключением на лету».

1. Создать Managed PostgreSQL в Amvera, регион **Warsaw-0**, тариф «Начальный»,
   диск 1 ГБ. Записать строку подключения.
2. `pg_dump -Fc` из Neon → `pg_restore` в новую базу (15 МБ, секунды).
3. `alembic upgrade head` на новой базе и сверка head: должен быть
   `0063_translation_cache` — тот же, что в коде.
4. Прогнать `/api/meta` против новой базы: `db.alembic_version` совпадает.
5. Переключить `DATABASE_URL` в переменных Amvera, перезапустить контейнер.
6. Проверка: `/readyz` → 200, `/api/meta` → head `0063`, вход по паролю,
   открытие ленты и «Моих задач», вебхук `pending 0`.
7. Через сутки сверить размер и число строк с исходником (`users`,
   `checklist_items`), затем остановить Neon.
8. Откат: вернуть прежний `DATABASE_URL` и перезапустить — данные в Neon
   остаются нетронутыми, пока проект не удалён.

Чего в этом плане нет и почему: `pg_upgrade`, даунтайма и «теневого» чтения.
При 15 МБ и восьми пользователях окно в 2–3 минуты на переключение переменной
безопаснее любой хитрой схемы.

## 6. Что это меняет в коде

Почти ничего: приложение уже работает с PostgreSQL по `DATABASE_URL`
(`asyncpg`), миграции те же. Нужно только:

* создать базу и переменные (это делает `tools/switch-db.py`/панель);
* убедиться, что `sslmode` в строке подключения поддержан (Amvera внутри
  кластера отдаёт подключение без обязательного TLS — проверить на месте);
* убрать из логов и документов упоминания Neon как «боевой» базы.
