# 🔐 Вход по почте в веб-версии (ЗАДЕПЛЕНО)

## Что сделано (коммит `635ca87`)

Шаг 2.1 B2B-плана закрыт целиком: почтовый вход появился не только в API, но и
в интерфейсе.

- `api/auth.ts` — вход, регистрация, выход, «выйти везде», устройства с
  отзывом, запрос и подтверждение сброса.
- `api/client.ts` — токен сессии в `localStorage`, заголовок
  `Authorization: Bearer`. Порядок старшинства: `initData` (мини-апп) → сессия
  по почте → ссылка доступа из бота. На 401 без `initData` забываются оба
  локальных токена — иначе приложение долбило бы сервер мёртвым заголовком.
- `features/auth/AuthScreen.tsx` — вход, регистрация и «забыл пароль» одной
  карточкой. Сброс отвечает «если адрес зарегистрирован, письмо в пути»:
  существование почты не подтверждаем.
- `features/auth/ResetPasswordScreen.tsx` + `resetUrl.ts` — страница
  `/reset?token=…`. Токен принимается **только** на `/reset`: иначе любой
  `?token=` в чужой ссылке открывал бы форму смены пароля. После успеха все
  локальные токены забыты (сервер уже погасил сессии), адрес очищен.
- `main.tsx` — развилка до `App`: ссылка из письма не поднимает приложение и не
  делает `GET /api/me` в 401 (проверено: на прямом заходе `/reset` запросов к
  API нет вовсе).
- `App.tsx` — 401 без `initData` показывает форму входа; внутри Telegram
  остался отдельный экран «Telegram не подтвердил вход» (подпись не принята —
  это не про пароль). 403 `org_required` → «аккаунт готов, ждём приглашения» с
  выходом; `org_inactive` → «организация на паузе».

# 🎧 GHG11 (17): окно приёма вариантов по режимам, сворачиваемый блок ленты, плеер вместо колокольчика (ЗАДЕПЛЕНО)

> **Запросы оператора:** 1) глобальная настройка «сколько принимаются варианты на
> активность» для каждого режима доставки (чат — как сейчас, чат + апп — как
> сейчас, мини-апп — расширить до 8 часов); 2) блок «Все события / Только мои / …»
> сделать сворачиваемым и разворачиваемым; 3) вместо колокольчика в шапке —
> плеер с выбором подборки за конкретную неделю или «всё последовательно /
> случайно», играющий без перерыва, а после конца подборки продолжающий «реже
> повторяемыми» треками; 4) тема день/ночь должна помнить последний выбор.

## 1. Окно приёма вариантов — своим числом на режим

Раньше окно сдачи голосового задания было ОДНО на все режимы (константа
`VOICE_TASK_WINDOW_MINUTES = 180` + окно конкретного задания из каталога). В чате
это правильно: задание видят сразу и сдают вживую. В мини-аппе (режим `app`)
задание приезжает в ленту — человек может дочитать её к вечеру, и три часа
истекали раньше, чем он вообще увидит задание.

Теперь у каждого режима доставки своё окно, настраиваемое в админке (Игра →
Голосовые задания):

* `game.voice.window.chat_minutes` — дефолт **0 = «как сейчас»** (окно из каталога);
* `game.voice.window.both_minutes` — дефолт **0 = «как сейчас»**;
* `game.voice.window.app_minutes` — дефолт **480 (8 часов)**.

Чистое решение вынесено в `voice.window_minutes_for(override_minutes, task)`: 0
(или мусор) — окно каталога, положительное — переопределение. Одно и то же число
уходит и в `expires_at`, и в текст задания: `build_task_text` теперь принимает
`window_minutes` (раньше обещал часы из каталога — при переопределении текст
разошёлся бы с реальным сроком). Потолок ручной настройки — сутки
(`VOICE_WINDOW_MAX_MINUTES = 1440`), зажим есть и на бэке, и на фронте
(`clampVoiceWindow`).

## 2. Блок управления лентой — сворачиваемый

Строка «Все события / Только мои / Фильтры / Действия» больше не занимает высоту
постоянно: у неё есть кнопка ▴/▾. В свёрнутом виде остаётся одна строка —
выбранный охват плюс честная сводка («все типы» / «типов: 2» / «скрыто
участников: 3»). При сворачивании закрываются раскрытые панели «Фильтры» и
«Действия», а переход из анонса (`feedAnchor === "feed-actions"`) сначала
разворачивает блок — иначе панель оказалась бы внутри свёрнутой строки.

## 3. Плеер вместо колокольчика

Повод для 🔔 был ровно один — лайки своих треков, и оператор справедливо не понял,
«что он предлагает делать с лайками». В слоте шапки теперь 🎧 (`PlayerButton`),
он открывает нижний шит (`PlayerSheet`):

* **▶️ Всё подряд** — подборки одна за другой (прежнее поведение);
* **🔀 Всё вперемешку** — тот же набор, порядок пересдан (SHUFFLE включается
  сразу: «слушать случайно» — одно действие, а не два);
* **❤️ Только лайкнутые**;
* **каждая подборка по неделе** — свой строкой, с числом треков; выбранная
  подсвечена (`aria-pressed`).

Выбор источника сразу начинает играть и закрывает шит. Выбранная подборка
играется целиком, а когда кончается — очередь НЕ зацикливается на ней: дальше идут

# 🛎 GHG11 (16): уведомления — нижний шит вместо сворачивания по колокольчику (ЗАДЕПЛЕНО)

> **Запрос оператора:** «вместо сворачивания по колокольчику придумай другую
> механику».

## Что не так было с прежней механикой

GHG11(13)/(14) оставляли колокольчик **тумблером**: тот же тап выдвигал панель
уведомлений и вдвигал её обратно. Панель стояла в потоке между шапкой и лентой,
то есть при каждом открытии лента теряла высоту (замер: `feed-scroll.top`
107 → 161), а выход из уведомлений был только там же, где вход — в колокольчике,
который на длинной ленте приходилось искать.

## Новая механика: нижний шит

Уведомления переехали в тот же язык, что лох, номинации и фильтр участников:
`BottomSheet` снизу экрана (`NotificationsSheet` в `NotificationsBell.tsx`, а
живёт он в `App.tsx` — вне шапки ленты именно потому, что шапка обрезает
переполнение `overflow-hidden`).

* Колокольчик — **только вход**: `onClick` всегда открывает, тумблера и
  `aria-expanded` больше нет ( `aria-haspopup="dialog"` ). Свернуть им нельзя по
  построению: шит перекрывает шапку.
* Закрытие там, где его ищут в мобильном: тап по затемнёной подложке, Esc,
  и любое действие системы. Отдельный крестик не нужен — он был лечением
  именно от механики «свернуть тем же колокольчиком».
* Лента больше не теряет высоту: панель не в потоке ленты вовсе.
* Список сам отмечает прочитанными, когда шит показан; бейдж — по-прежнему
  «сколько нового».
* В `BottomSheet` добавлены `data-testid="sheet"`/`sheet-backdrop` и
  `role="dialog"` с `aria-label` — шит стало можно проверять тестом, не
  подглядывая в классы (правка аддитивная, чужие шиты не меняются).

# 🌙 GHG11 (3): шар в ленту, ачивки шара, каскадное удаление и планировщик (ГОТОВО К ВЫКЛАДКЕ)

## Что сделали

- **Магический шар — результат в ленту, а не в шапку.** `POST /api/game/advice`
  принимает `{question?, target}`. По умолчанию (`target="feed"`) пишет запись в
  ленту от лица игрока: «🔮 Серж покрутил магический шар и получил ответ…», а если
  задан вопрос — «...задал вопрос магическому шару: «…» — и услышал: ...».
  `target="header"` возвращает текст в ответ (старое поведение, кнопка «📌 В шапку»).
- **10% «Иди на хуй».** На любой вопрос с шансом 10% шар посылает — за это отдельная
  instant-ачивка `advice_sent` («Иди на хуй», 🖕). База `advice_seeker` («Пифия») —
  «спросил впервые» + юбилей ×10 (`COUNTER_ADVICE`). Раздел — «🎲 Звания и рулетка».
- **Кнопка троеточия → глазик 👁** в записи ленты (выпадает «скрыть у себя / удалить»).
- **Каскадное удаление.** Админское удаление записи ленты СТИРАЕТ её источник из
  БД (`journal:`/`voice:`/`music:`/`music_game:`/`loser:`/`chukhan:`) — чтобы не
  оставалось «фантомной задачи», блокирующей запуск новой. Ачивки (`ach:`) не
  стираем (факт биографии). Если источник удалён физически, «Отменить» в плашке не
  показывается (`FeedItemActionOut.hard`).
- **Аварийное схлопывание задач.** `scheduler` ведёт `_RUNNING_SINCE`; watchdog
  каждые 5 мин находит job, провисевший > `STALE_JOB_SECONDS` (15 мин), и
  пересобирает планировщик с нуля, чтобы он не блокировал следующий запуск.
- **Мастер-кнопка «схлопнуть все запланированные авто-задачи»** —
  `POST /api/admin/scheduler/collapse` (и кнопка 🧨 на экране «📋 Очередь задач»):
  `collapse_all_jobs` гасит и заново поднимает планировщик (как рестарт спейса).
- **Прогон фразы из аппа.** `POST /api/game/phrases` (админ) — фраза СРАЗУ в ленте,
  без `user_chance` и без блокирующей плашки.
- **Ручная рулетка в ленте.** Запись о ролле пишется явно: кто крутил, кто выпал,
  причина и выданная за это ачивка («Искатель истины», +50 XP).
- **Подробный гостевой профиль.** `GET /api/game/players/{id}` теперь отдаёт
  историю «лоха дня»/«чухана недели» (когда и за что), суммарные дни владения

## Проверка точки отката (настоящая, а не «файлы на месте»)

```bash
python tools/db-rehearsal.py info                      # какие базы есть, какая боевая
python tools/db-rehearsal.py rehearse backups/<штамп>   # пустая база → дамп → сверка
```

`rehearse` создаёт **отдельную пустую** базу (`ghg_rehearsal_<штамп>`) на резервном
инстансе (если в `leltokens2.txt` только один DSN — на том же, с предупреждением),
прогоняет `alembic upgrade head`, заливает дамп и сравнивает слепки.

Важная деталь методики: восстановленное сравнивается **с дампом**, а не с боевой
базой. Боевая база живёт и пишется — сравнение с ней ловит не дефект
восстановления, а свежие записи. Дрейф боевой базы с момента дампа печатается
отдельным блоком и не влияет на вердикт.

`restore` в `tools/backup-db.py` — это upsert, а не `insert … on conflict do
nothing`: миграции засевают часть таблиц (например, дефолтный Новый год в
`game_holidays`), и `do nothing` молча оставляла бы засеянную строку вместо
строки из дампа. Плюс после заливки пересчитываются последовательности
(`setval` по `max(id)`), иначе следующий INSERT в приложении падал бы с
duplicate key на восстановленной базе. Отключить удаление «лишних» строк (тех,
которых нет в дампе): `--no-prune`.

## Транзиентные сбои фоновых job'ов

Фоновый прогон больше не падает целиком из-за секундного сетевого блипа. Тюнинг
без деплоя кода — переменными окружения контейнера:

- `SCHEDULER_DB_RETRY_ATTEMPTS` (дефолт 3) — сколько всего попыток прогона;
- `SCHEDULER_DB_RETRY_BASE_DELAY_SEC` (дефолт 2.0) — базовая пауза, растёт
  экспоненциально (2с, 4с, 8с…).

Ретраятся только транзиентные сбои подключения (DNS/сокет/таймаут/`OperationalError`).
Логические ошибки БД валят прогон сразу — их маскировать нельзя. Смотреть в логах
`scheduler.job_retry` (повтор), `scheduler.job_failed` с `transient=true` (сдался)
и `job_id` в обоих.

## GHG11 — единая модель доставки бота (off / chat / app / both) + правки

### Ядро: `services/game/delivery.py`

- НОВЫЙ модуль. Каждая функция бота описывается одним из ЧЕТЫРЁХ состояний:

## 24.10.2026: почему /changelog молчал — сеть контейнера, а не команда

Владелец прислал скрин: `/changelog` в 01:11, 02:00 и 02:28 — две галочки, ответа
нет. Разбор шёл не по догадкам, а по живым логам Space и новой диагностике.

Что было видно в логах HF:

- один и тот же апдейт (`id=296484299`) обрабатывался по 190–194 с, снова и
  снова (Telegram повторял доставку, потому что не получал ответа);
- каждая отправка — `TelegramNetworkError` / `Request timeout error`;
- при этом `httpx` в том же контейнере тянул `api.github.com` за 200 OK.

Что показала новая ручка `GET /api/meta/net` (доступ — по `X-Diag-Token:
<TG_WEBHOOK_SECRET>`, без него 404):

| Проверка | api.telegram.org | workers.dev (воркер) | api.github.com |
| --- | --- | --- | --- |
| DNS | 149.154.166.110 (верный) | 104.21.x / 172.67.x | 140.82.112.5 |
| TCP :443 | ok, 80 мс | ok, 3 мс | ok, 2 мс |
| TLS | **таймаут 6 с** | **таймаут 6 с** | ok, TLSv1.3, 14 мс |
| TLS без SNI | таймаут | таймаут | ok |
| aiohttp GET | таймаут | таймаут | 200, 16 мс |
| httpx GET | — | — | 200, 20 мс |

То есть контейнер стучится по правильному адресу, TCP открывается, а
рукопожатие TLS до сети Telegram и до Cloudflare не завершается вовсе (и с SNI,
и без него). GitHub при этом работает и на aiohttp, и на httpx. Вывод: это выход
площадки HF, а не код команды и не DNS-подмена. Кодом это не лечится — нужен
другой путь наружу (свой прокси в пуле или хостинг с рабочим egress).

Что всё-таки сделано в коде (чтобы сбой был слышен и не растягивался):

1. **`/changelog` больше не съедает окно вебхука.** `Message.reply(...
   request_timeout=12)` в aiogram 3.x на сетевой таймаут не влияет (уходит в
   поля `SendMessage`), поэтому одна попытка жила по таймауту сессии. Теперь
   попытку рвёт `asyncio.wait_for(12)`: три попытки + короткий ответ без
   разметки укладываются в минуту. Тест `test_deliver_cuts_a_hanging_send_by_its_own_timeout`
   держит это поведение.
2. **Обходной путь мимо `BOT_API_SERVER`.** После сбоя основной дороги — одна
   короткая (8 с) попытка напрямую на `api.telegram.org`; успех пишется в лог
   `telegram.direct_fallback_ok`. Смысл: одна мёртвая дорога больше не глушит
   бота целиком.
3. **Пин IPv4 стал флагом, а не константой.** `BOT_FORCE_IPV4=false` раньше
   отключал только класс сессии — коннектор оставался IPv4. Теперь семейство
   берётся из флага (`_connector_family`), по умолчанию по-прежнему IPv4: у
   этого контейнера IPv6 нет вовсе (connect — `OSError` за 1 мс).
4. **Телеметрия отправки.** `telegram.request_failed` (класс ошибки, хост, мс) и
   `telegram.request_slow` (успех, но дольше 2 с). Раньше единственным следом
   был `Request timeout error` без адреса и тайминга.
5. **Грабля логирования.** `log.warning(..., method=…)` в `dispatcher.py`
   (там stdlib `logging`) бросал `TypeError: Logger._log() got an unexpected
   keyword argument`, и **настоящая** ошибка сети подменялась ошибкой лога — так
   в логах появилось `webhook.set_failed: Logger._log() ...`. Теперь все поля
   идут через `extra={…}`; тест на путь отказа это ловит.
6. **`deploy-hf.py` не роняет Space.** Секрет с именем, которое уже занято
   переменной Space, даёт `CONFIG_ERROR` («Collision on variables and secrets
   names») — именно так Space один раз лёг целиком. Теперь такие имена
   пропускаются с явной строкой в выводе.

Проверки: `pytest` — 62 теста в затронутых файлах (`test_meta`, `test_net_pool`,
`test_round5_weekly_profile_changelog`, `test_help_commands`), `ruff` чисто по
`routes_meta.py`, `test_meta.py`; по `dispatcher.py` остались только два
прежних замечания (`I001`, `UP041`), новых нет. Выложено: HF Space RUNNING,
`/healthz` 200, `/api/meta` 345 путей, head `0059_email_verification`.

Что осталось: сам выход в Telegram. Варианты — свой SOCKS5/HTTP-прокси в пуле
(механизм уже есть: `ProxyScreen`, `PROXIES_BOOTSTRAP_JSON`, режим ALWAYS_ON)
